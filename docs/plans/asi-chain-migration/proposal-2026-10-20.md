## 1. Summary

**What forces client changes.**
- Every ASI deploy path builds a legacy body-only deploy today. The target refuses those deploys [CB F1]. Each path must sign an owner-direct offered envelope instead. That is the same envelope the node's own CLI signs (`casper/src/rust/util/rholang/costacc/owner_offer.rs:82-177`).
- Most ASI clients talk to the ASI **Scala** node. Moving to the Rust-based target also forces two more changes:
  - the system URI names change [CB F6];
  - the explore request takes a JSON body [CB F7].

**What each kind of client needs.**
- The Rust clients can call the node's public builder `owner_direct_offer` directly. This is a small change in one function per client.
- The TypeScript wallet and SDK need a port of the envelope encoding. The port must be checked byte for byte against vectors that come from the node's builder. This is the largest single work item.

**Owner funding.** No ASI service installs a stored contract. So G3 owner funding gives ASI operators no funding duty. It only affects contracts that users deploy through the wallet or the CLI [RC F12].

**Cut-over.** There is no rolling upgrade. The target cannot replay legacy blocks, so ASI needs a fresh protocol-6 genesis seeded from a balance export of the legacy chain [CB F8].

**Two stages of client work.**
- **Can start now, against [CB]:** envelope construction, URIs, the explore body, deploy-ID handling, configuration and genesis.
- **Must wait until B4 to B6 settle [TB]:**
  - waiting for the executed outcome;
  - resubmitting after a gate rejection;
  - the new meaning of block fields in the indexer and explorer;
  - retrying when the pool is full;
  - sizing phlo limits to the per-block demand cap;
  - waiting longer for bonds because of the epoch lag.

**Timing.** Production cut-over comes after B8. The design estimates about ten calendar months for B0 to B7 (stall-loop :698), so the cut-over is months away (inference).

**Effort, in agent time (§14).** The work that can start now is about 49 agent-hours, plus 5.1 hours to re-check it on the campaign-final node. With 4 agents in parallel it takes about 19 hours elapsed under the host's one-heavy-job-at-a-time rule, or about 14.4 to 15 hours if separate repositories may build at the same time. The work after Track B is about 49 agent-hours, which is about 15.5 to 17 hours elapsed. One agent-hour is one hour of wall-clock time of one Claude agent working on this host, including its builds, tests and one review round.

**No change to the limits.** Under the legacy model the deploy precharged phloLimit × phloPrice. The offer's REV ceiling is phloLimit × phloPrice + 1, so the signer accepts the same maximum cost (DR-134 item 6, :17385-17392). **API surface for other projects.**
- All existing signatures stay: `deploy`, `deploy_with_phlo_limit`, `full_deploy`, `deploy_and_wait`, `transfer`. The returned deploy ID is now 64 hex characters (F3).
- Signing and signed price consent happen inside the envelope. The schedule's actual price, the price ceiling and the required owner ceiling all equal the signed price (`owner_offer.rs:95-98, 143-150`).
- The dry-run estimate uses the existing `estimate_cost` and `exploratory_deploy` (F9). There is no new API.
- A receipt read (F10) is not needed on [CB]. It is added in Phase 3 if the Track B outcome API uses the receipt route (N1).

**Changes after Track B [TB, wait for B4 to B6].**
- **R-T1** (`connection_manager.rs:235-460`): wait for the executed outcome, not for the finalization status (F17, F18; API per N1 and N3).
- **R-T2** (`query.rs:106-139`): read data at executed(b), not at the block's post-state (F14; N2).
- **R-T3**: after a gate rejection, build a new envelope with a new timestamp, which gives a new ID (F17).
- **R-T4**: retry on 503 `deploy_pool_full` (F13).
- **R-T5**: keep limits at or below the demand cap. The 5B mapping may have to go (F15; Q-8).
- **R-T6** (`events.rs`): deduplicate by `commit_epoch` if it reaches `/ws/events`, and use an executed event if N7 adds one (F13, conditional).

**Owner funding.** rust-client installs nothing. Its vault and PoS terms call genesis contracts, which have no owner purse (DR-68 item 4).

## 7. Owner funding (G3) effects [RC]

**The rule.**
- A fired stored body runs for its owner at the owner's recorded price.
- If the owner cannot pay, the interaction does not fire, nothing is charged, and the caller's run continues and settles. Replay checks the refusal, but the receipt does not show it (DR-135 items 1-6 and 8, "Not adopted" :17737).
- An installation signed `[s1 -o s2]` moves the body's cost to s2. A sponsor funds s2 through its vault address (DR-68 amendment :4888-4890; `offered_owner_api_test.rs:667-760`).
- Genesis contracts are Unit-signed and have no owner purse (DR-68 item 4; the DR-101 amendment :4853-4858).
- Under the caller-only reservation, the caller's limit and hold cover only the work the caller pays.

**What ASI's own services install.** Nothing:
- the faucet and wallet transfers call SystemVault;
- the bot deploys `stdout.rho`;
- the validator connector bonds through PoS, a genesis contract;
- the indexer and explorer only read.

So ASI operators have no owner-funding duty.

**User-deployed contracts.** When a user deploys a contract through the wallet's Deploy or IDE page or the CLI, the deploying key becomes the owner. If that vault is empty, other users' calls do not fire, and their deploys still succeed (`offered_owner_api_test.rs:475`). The operator should document this: an installer funds its own vault, or uses a funding slot.

**Effect on estimates (inference).** The dry run does not model owner funding (F9). For calls into owner-funded contracts it counts owner-paid work and fires interactions that would be refused for real.

## 10. Rollout and compatibility

**No compatibility is possible.** The target refuses body-only deploys (F1) and cannot replay legacy blocks (F8). Without a dual mode, migrated clients cannot reach the legacy node either. So there is one coordinated cut-over.

**Cut-over steps.**
1. Announce a freeze, then stop deploy intake on the legacy chain.
2. Export balances at block N with `asivaultexport`.
3. Build the genesis: wallets, bonds, the policy, token metadata, and the v6 activation when [TB] applies.
4. Start the target validators and observers.
5. Release the migrated services and clients together. The SDK gets a major version because S-2 changes its API (inference).
6. The indexer starts a new database.
7. Check balances against the export.
8. Open the network.

**History.** The legacy indexer database can be kept read-only (Q-U5).

**Rollback.** Before the network opens, ASI can go back to the legacy chain. After it opens, it cannot, because the new chain's state diverges (inference).

## 12. Risks, and parts of the node that are still changing

**Risks.**
- **The TypeScript port must be byte-exact.** An encoding change in the node makes every TypeScript offer fail admission. Mitigation: pin the node version and regenerate the vectors for each release.
- **Rejections are silent on [CB] (F4).** Mitigation: client timeouts, WC-2 and N4.
- **The transfer phlo margin is about 10%, and G3 and B2 may change charges.** Mitigation: re-measure in P2 and P3.
- **The demand cap may force lower limits** (5B, 100M) (Q-8).
- **Rust client builds.** The `casper` dependency adds weight, and the toolchain may need to change (inference).
- **Balance reads lag executed state under [TB].** The faucet's eligibility check reads lagging state (inference).
- **The cut-over is one-shot.** Mitigation: the P4 rehearsal.
- **Schedule risks (§14).**
  - A byte mismatch between the TypeScript encoder and the vectors adds 1 to 3 hours on the critical path.
  - The wallet, explorer and faucet web app have no lockfiles. Today's dependency versions may break a build for reasons unrelated to the migration. Mitigation: build in containers, and report such breakage without fixing it (scope rule).
  - Docker image builds run in the Docker daemon's own control group, outside the host's 40G memory cap. Mitigation: set a capped build method before the first image build.
  - Heavy jobs from other workspaces on the host slow the one-heavy-job schedule.

## 15. Side notes (not part of the migration)

- The explorer sends a hard-coded Hasura admin secret from the browser (`walletService.ts`).
- `asi-chain-wallet/src/services/rchain.ts:56` hard-codes a fallback GraphQL IP.
- The wallet reserves 0.0025 ASI before sending. A 500k-phlo deploy needs 0.005 ASI, under both models (`constants/gas.ts:1-24`; `Send.tsx:299`).
- The wallet's fallback scans `/api/blocks/10` for deploys, but that list omits deploys on both nodes.
- The faucet multiplies `FAUCET_MAX_BALANCE` by 10^8 (`config.rs:31`; `transfer.rs:35`).
- The faucet web app defaults token decimals to 9 (`web/src/utils/config.ts:30`); the node uses 8.
- The fee displays (SDK `GasFee`, the wallet's random fee) do not reflect real usage.
- The indexer labels SystemVault transfers as `smart_contract`.
- `asi-local-launch.yml` passes stale indexer environment variables (`RUST_CLI_PATH`).
