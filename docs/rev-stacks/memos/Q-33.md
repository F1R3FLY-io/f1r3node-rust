# Q-33: P11 in v6, no block is final until its state is known

Lane A2, 2026-11-03. Reference: design r18 (P11, Decision 98), and the Casper Working Group's finalizer response (`cost-accounting/stall-loop-design-5-10-1-response.tex`, here "CWG"). Base: `patch/FX-15-replay` at 7ac56f01a.

## Today

- The finalizer (CWG Compute, Validate and Commit: `floor_runner`, then `validate_commit` in `commit_lfb`) gives the LFB from the safety oracle on order.
- `V6Engine::tick` gives that LFB to the linearizer. The linearizer emits the LFB's epochs in order, and the executor core runs them.
- So a block is final before any node executes it. Its state becomes known later: a cited record is fixed by replay, and attestations are checked against the fixed root.

## 1. Execution

Split the two meanings of "finalized":

- **Order floor (OF):** the block that the order oracle certifies. This is the CWG `Advance(F)` after preconditions P1 to P4.
- **LFB:** the order floor, clamped to the highest block whose state is known (P5, item 2). This is dev's meaning.

The linearizer follows the order floor, not the LFB. Execution then runs the ordered but unfinalized prefix, between the LFB and the order floor. That prefix cannot reorganize, because the order oracle has certified it. So execution in this prefix is not speculative about order, and the existing `ExecutorCore` runs it unchanged:

- emit, then own execution in `spec`;
- citations and replay fix the canonical records.

`max_speculation` (32) keeps its present role: it bounds how far own execution runs ahead of the fixed canonical records. A new bound, `max_unattested`, limits how far the order floor can run ahead of the LFB (item 4).

## 2. Finality

**The rule.** A block B at linear position k is final iff both of these hold:
- B is at or below the order floor;
- attestations from more than 2/3 of the bonded stake name the same post-state root R for position k, or for a later position j > k.

An attestation is the `(block_hash, root)` pair in a v6 block body. One attestation covers every earlier position, because execution is deterministic over a certified prefix.
- Stake comes from the bonds at the current LFB. CWG σ already folds in the LFB, so bonds stay a function of σ.
- Under θ ≤ 0 there is no state finality. This is the same terminal hold as CWG's incompatibility rule.

**Where the check lives:**
- **Finalizer (Validate):** P5 is a new precondition in the `validate_commit` closure that `commit_lfb` runs under `global_lock.write`. It clamps F to the highest main-chain block at or below F that P5 accepts. It refuses with a new `CommitRefusal::StateUnattested` when that block is not above the current LFB. P5 is a lookup, so it does not add work to the budgeted Compute phase.
- **One transaction:** the order floor gets its own one-row register. It is written in the same LMDB transaction as the commit marker and the LFB pointer, so crash reconciliation recovers both.
- **Linearizer:** `V6Engine::tick` reads the order floor register instead of `last_finalized_block()`. The A-LIN check stays on the order floor.
- **Attestation tally:** a new index that `observe_block` fills, keyed on the attested block and stake-weighted by validator. P5 reads it. The tally keeps the latest attestation of each validator.
- **Conflicts:** a validator that attests a root different from R for the same position is a `Misattestation`, as `fix` reports it today.

## 3. Invalid blocks

The case: a block B in the certified order whose execution shows it invalid, for example an uncovered close.

**Option A: reject the blocks built on B.**
- This is not possible after order certification. The oracle has already certified the descendants.
- The honest proposers who built on B could not know, because execution comes after order.
- One Byzantine block would invalidate every honest block above it.
- Do not use.

**Option B (recommended): B is void.**
- B's record is a void record: post-root = pre-root, every envelope refused, and the envelopes go back to the pool with a rejection entry.
- Descendants run on that pre-state as usual. Every honest executor derives the same void record, so the attestations converge and P5 passes.
- **DAG:** no change. B stays an ordered message, and its justifications still count for the oracle and for equivocation.
- **Evidence:** a new `Offence::VoidBlock { reason }` names B's sender. It is a safety-class offence, and it is slashed with B6. No neglect rule is necessary, because the void record is deterministic.
- **The close:** a void block does not run its close. PoS close logic must then trigger an epoch at the first block at or above the boundary, not only at the block equal to it. Lane B must confirm this for `PoSV6.rhox`.

**Effect on Decision 97:**
- The acceptance check reads the attested root, which is not the execution pre-state, so it cannot be exact. Under P11 it is not necessary.
- An uncovered close at execution becomes a void block. Decision 97's open item, a hold less than the pre-charge, closes, and no close work goes unpaid.
- `create_block` keeps its own check as a courtesy.

## 4. Stall analysis

The Issue #24 loop was a finalizer that discarded its work on timeout. CWG resumable derivation removes that loop. P11 adds a dependency: LFB ← attestations ← execution ← order floor. The question is whether a path goes back from the LFB to order or to execution:

- **Order:** the oracle reads the latest messages and the DAG. P11 makes the LFB slower, so σ changes less often. That reduces CWG cursor resets.
- **Execution:** execution reads the order floor, not the LFB. No path goes back.
- **Bonds:** bonds come from the LFB, so a validator-set change takes effect one attestation round later. This is a latency, not a loop.
- **Load:** the existing `LagGate` empties proposals when execution falls behind. That is damping, not amplification.

So the loop does not come back. Two bounds hold:

- **Finality lag** is at most order-oracle lag + E + A.
  - E is the time to execute the backlog. The `LagGate` keeps it bounded, because blocks above the lag threshold carry no envelopes.
  - A is one round in which more than 2/3 of the stake proposes after it executes.
- **Storage** grows while more than 1/3 of the stake does not attest. This is the standard BFT liveness assumption, the same as the order oracle under θ > 0. In that case, order and execution continue and the LFB stops. States and records above the LFB must stay resident. `max_unattested` engages the `LagGate` on the distance from the LFB to the order floor. Growth is then limited to empty blocks.

**Risk:**
- **Clients:** an API client that waits for finality waits one more attestation round. Deploy status ("finalized") then means that the state is known. This is P11's purpose, but it changes the observed latency.
- **dev:** dev has no `commit_lfb` or `floor_runner`. The P5 hook lands in this branch's CWG code, and the `dev` merge must keep it.

**Decision 97 code changes:**
- Remove `check_close_cover` from the validation dispatcher after the ruling. Until then it stays as committed. It is inert at the default pre-charge of 0, and no code changes until the ruling.
- Keep the `create_block` self-check.
- In `gate_block_with_close`, a hold less than the pre-charge makes the block void, in place of a partial hold.
- Keep `SystemCharge` and the policy field.

**Schedule:** P11 does not fit the Friday handoff. The order floor and P5 are consensus changes, with a multi-node test burden. Either the handoff slips about a week, or it goes with P11 as a known divergence and the order floor as the finality that is reported. This decision is yours.

## Recommendation

- Split the order floor from the LFB, with P5 in `commit_lfb`'s Validate.
- Void, not reject.
- `max_unattested` as the storage bound.
- Remove Decision 97's acceptance check after the void path lands.
