# P2-21 decisions: native REV moves leave the run (M-6)

Patch P2-21, rev-stacks patch plan r7.2, lane B. Branch `patch/P2-21`, cut
from `patch/P2-11`. All code in this patch is new. Nothing is ported.

## Ruling (2026-10-30)

M-6: each run's native REV debits and deposits are carried out of the run and
applied at settlement, in block order, in the canonical form, and bounded by
the gate's commitments. The ruling named this option (a). In the memo it was
option (c). A short memo on the labels went out before the work started. The
build follows the ruling as written.

## Files touched

- rholang (lane C's native layer): new `rev_stack/journal.rs`. `native.rs` (`transfer`, `balance`) and `bond.rs` (`bond`) use the journal when one is open. `owner.rs` gets `WalletOwner::from_canonical_bytes`, moved from `hooks.rs`.
- casper: `v6/executor.rs` (shared with lane A2), `v6/settle.rs`, `v6/history.rs`.

## Decisions

| # | Decision | Alternatives | Reason | Reversible |
|---|----------|--------------|--------|------------|
| 1 | Before each gated run (play and replay), the executor opens a native journal in the run's hot store: a marker datum and a journal channel, both hashed from domain tags. While it is open, `rho:rev:wallet transfer` and `rho:rev:bond bond` record `(from, to, amount)` in the journal and write nothing to the wallets. After the run, the executor reads and clears the journal before the checkpoint, so the journal leaves no trace in the run's post-root. | Keep native writes in the run and teach the merge about them. | Ruling. The run's state then holds no native REV movement, so the merge cannot drop or double one. | Yes |
| 2 | Inside a run, a read shows `balance + journaled credits − journaled debits − visible`. A journaled spend needs `amount ≤ balance + credits − debits − held`, where `held` is the block's commitment on the wallet (M-5). A process-wide lock serializes check-and-record. | — | Reads stay consistent within the run, and the gate's commitments stay out of reach. | Yes |
| 3 | A run that fails or is exhausted is rolled back to its soft checkpoint, and its journal is rolled back with it, so it moves nothing. A run that loses the merge keeps its journal, but its moves are not applied. | Apply the moves of every admitted run. | A run's REV moves are part of its effect. | Yes |
| 4 | One native payer per wallet per block: before the merge, a later admitted run whose journal debits a wallet that an earlier candidate run already debits is treated as conflicted. | Apply both and refuse the second at settlement. | Each run's spends are bounded against the pre-state. With one payer per wallet, the charges (bounded by `held`) and that payer's moves always fit together, so settlement never refuses a move it already reported as a success. Deposits commute, so many runs may pay into one wallet. | Yes |
| 5 | Settlement, in block order: the charge debits (each paying wallet ends with one combined datum), then the kept runs' moves in block order (native transfers, deposits as separate datums), then the proposer and compute-wallet deposits. Then the REV hook and the conservation check, which also covers the move parties. | Moves before charges. | The canonical form and Decision 9. Charges first keeps them inside the commitment. | Yes |
| 6 | The record carries the applied moves in `SettlementProto` field 6 (`TransferProto`: envelope, from, to, amount, with owners in canonical bytes). Replay journals each run again, settles again, and refuses a record whose moves differ. | — | Replay must reproduce what it accepts. | Yes |
| 7 | P2-20's history gives the moves as `TransferKind::UserTransfer`. | — | Closes the gap that P2-20 left open. | Yes |

## Tests

- `rholang/tests/rev_reserve_spec.rs::an_open_journal_holds_transfers_out_of_the_state`: with the journal open, a transfer succeeds without touching the wallets. The read shows the journaled balance. An over-spend is refused. Closing the journal returns the one move and closes the journal.
- `casper/tests/v6/gated_executor_spec.rs::a_user_transfer_and_bond_survive_play_and_replay`: one user deploy transfers 6,000 REV to Bob and bonds 1,000 through `PoS!("bond")`. At the block's post-root, Bob holds 6,000, the bond channel holds 1,000, PoS lists the bond, and Alice holds 100,000 − 7,000 − her charges. The history gives both moves. The record replays to the same post-root. A record with a forged move fails replay.
- `one_run_per_block_pays_natively_from_a_wallet`: of two runs that pay from Alice natively, the later one is conflicted and its move is not applied. A run that pays from Carol in the same block is kept. Bob receives both kept moves. Replay gives the same verdicts, settlement and settled root.
- `a_run_cannot_spend_the_rev_its_block_has_committed` now checks that the allowed transfer lands at the settled root.
- All P2-05 to P2-20 tests pass with empty journals.
