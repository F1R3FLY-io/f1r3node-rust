## D-P0-12-2 — The group cap is configuration

- **Decision:** Track A hard-coded the group cap (16). The patch adds `casper.rejection-search-group-branch-cap` (default 16) next to Track A's `rejection-search-cap-from-height` (default unset). `RejectionSearch::for_block` takes the cap as an argument.
- **Reason:** Caps and limits are configuration parameters.
- **Reversible:** yes.

## D-P0-12-3 — The deduplication removal in compute_rejection_options is safe

- **Decision:** Keep Track A's change in `rspace++/.../merging_logic.rs`. It removes a linear search for an equal option before each insert.
- **Reason:** `result` is a `HashSet<HashableSet<_>>`. `HashableSet` equality is set equality and its hash does not depend on order, so the insert removes duplicates by itself. The result does not change. The change applies at all heights. It changes only the time, not the merge output.
- **Reversible:** yes.

## D-P0-12-4 — ESCALATION: the activation height and the group cap change the state root

- **Status:** Escalated on 2026-10-30. Meredith accepted option 1 on 2026-10-30.
- **Finding:** From the activation height on, the greedy fallback can choose a different rejection set than the exhaustive search. A different rejection set gives a different merged post-state. The proposer and every validator compute the merge from the same parents, so all validators must use the same two values. If one validator uses a different height or cap, it computes a different post-state for a merge block and rejects blocks that the others accept.
- **Where the values come from:** Both values enter through the node configuration (`CasperConf` → `CasperShardConf`), like Track A. Other shard-wide values, for example `deploy-lifespan`, already come in this way, and the operator must keep them identical across the shard. Nothing checks that they match.
- **Options:**
  1. **Recommended.** Land the mechanism with the activation height unset by default, so the merge stays exhaustive and equal to dev. Mark both keys as shard parameters in `defaults.conf`. Before any shard sets a height, move the two values to a source that all validators share (genesis or on-chain shard configuration), or put them in the protocol version as a fixed fork height.
  2. Make both values compile-time protocol constants with a fixed fork height now. This removes the risk of a configuration mismatch, but it fixes the height before the soak gives data for it.
  3. Drop A9 from phase 0. Large conflict groups then keep the exhaustive search and its exponential cost.
- **Decision:** Option 1. The activation height stays unset by default. Where the shard parameters live must be decided before the first activation.
- **Reversible:** yes while the height stays unset. Once a shard activates the cap, the activation is irreversible for the blocks after that height.
