# D79 decisions: purses at the seal, data records, and the matcher filter (lane C)

Branch `patch/D76`, lane C, on top of lane A2's D76 after the r8.10 rulings (f92b58dc7, which has `patch/FX-13` merged). Lane A2's hook note is `D79-matcher-hook.md`. Design revision 11, plan r8.10. Decisions 79, 80 and 81 answer Q-31. This branch builds lane C's part of them. Lane B builds the FX-12 part (Decision 82, F35).

## Before this branch

- D76 charged each surface of a COMM one cell, keyed by the seal. Only continuations had a record (FX-2). A datum from an earlier block was a client surface (D76 gap 1).
- Any stored receive was a match candidate, also when its purse could not pay for its cell. D76 capped the draw at what the purse held (D76 decision 7).
- FX-13 removed the data mark. The tests did not cover a transfer from the sender's own identifier inside the receiver's evaluator.

## Decisions

| # | Decision | Alternatives | Reason | Reversible |
|---|----------|--------------|--------|------------|
| 1 | `SealRecord::purse()` gives the wallets that the record draws on: the owner's wallet, or each component of a compound owner (Decision 24). `SealRecord::price()` gives the origin's price. `seal::purse_of` is the one rule, and D76's `surface_purse` now calls it. | A separate purse for each channel. | Decision 79: a wallet wraps a purse, and the seal record locates it. There is no `fundPurse` and no `drainPurse`. | Yes |
| 2 | `SealRecord::shares_membrane` is true when the owner and the origin are equal. | Compare the owner only. | Decision 80. | Yes |
| 3 | `comm_ledger::comm_cells(receive, sends)` is a pure function of the records of a COMM. It gives one key for each distinct membrane. A side with no record is the key `None`, which is the client of the run that fired the COMM. `left_in_space_match` calls it at D76's call site. | Keep the set construction inline. | Decision 80 and Decision 81. The function is the one place that counts cells, and a unit test covers it. | Yes |
| 4 | The key of a cell is D76's `Surface`: owner, envelope and price. The origin's signers are not in the key, because the envelope fixes them. | Add the signers to `Surface`. | The record entry (field 18) encodes `Surface`. A change would change the record encoding for no change in the count. | Yes |
| 5 | A `None` side and the client's own record are two keys, as in D76. A COMM between the client's send and genesis code counts two cells, and the client pays both. | Map `None` to the client's record before the comparison. | Decision 80 gives one cell only for one membrane. Genesis code has no membrane. D76 already counts this way, and its tests depend on it. Lane A2 and the maintainers can change this in `comm_cells` alone. | Yes |
| 6 | A datum carries the record of the send that stored it, in `ListParWithRandom` field 3 (`seal`). Only the reducer's `eval_send` writes it, and only when seal records are on. The matcher copies it to the matched datum. Native acks, contract calls, and cells that the REV layer writes carry no record. | A side table in the storage rule. | D76 gap 1: the storage rule's payers live for one run only. A datum stored in an earlier block must name its sender. | No: field 3 is part of the datum encoding when present. |
| 7 | A datum without a record keeps the legacy bytes. The binary encoding is the pars, then the random-state length, then the random-state bytes. Bit 63 of the length is set when a record follows the bytes. JSON leaves out an absent `seal`. Equality and the hash include the record only when it is present. | A tag byte in front, as on the continuation. | The legacy layout has no tag byte that we can use. The length of a random state never comes near 2^63. The tests check the fixed and the variable integer encodings of bincode. | No |
| 8 | At a COMM, a stored datum is charged to the record on the datum. If the datum has no record, the storage rule's payer applies, as in D76. The send that fired the COMM is still the running record. | Read the storage rule first. | The record on the datum is the same in play and replay, and in every later block. | Yes |
| 9 | `Match::admits_waiting` is a new hook with the default `true`. `extract_first_match` calls it for each waiting continuation before it tries to match the data. The rholang matcher gives `seal::funds_continuation`. The hook applies only to stored receives. The consume path does not call it, because a receive that matches at once is not stored. Replay of a send goes through the same `extract_first_match`, so replay re-checks each logged COMM with a stored receive. The replay consume path needs no hook: there the stored side is data. | Veto in `check_commit`, as `D79-matcher-hook.md` proposes. | `check_commit` also runs on the consume path, where it would test the new receive (the running record) against a foreign purse. The new hook also skips the spatial match of an unfunded candidate. Lane A2 owns the match coordinator and must accept the hook point. | Yes |
| 10 | The funding test is a task-local `seal::Funding` oracle, `funds(&SealRecord)`. It takes the whole record, not the owner and price of `FundedReceive::can_pay`, so that the oracle can see the origin (decision 11). The executor installs it on the runtime (`set_funding`), and `inj` scopes it. `seal::inherit` and the deferred dispatch spawn keep it. Without an oracle, every candidate is funded. | Store the oracle in the matcher. | One `Matcher` serves all runtimes of a pool. The oracle belongs to one envelope run. | Yes |
| 11 | The casper oracle (`v6::surface::EnvelopeFunding`) funds a record of the running envelope without a test, because the client pays for its own surfaces (D76 decision 5). For another envelope's record, each wallet of `purse()` must hold at least `price()` at the block's pre-state, less what the gate commits from that wallet for the block. `BlockPurses` reads each wallet once for each block and shares the reads between the runs. | Read the run's live balance. | Decision 79: the pre-state balance less what the block holds. The live balance changes during the run and depends on the order of parallel branches, so play and replay could disagree. The pre-state and the gate table are the same in play and replay. | Yes |
| 12 | A funded receive is still drawn at settlement with D76's cap. The close-of-run check (Decision 48) and the block check (Decision 49) do not change. | Reserve the cell at match time. | Decision 79 keeps those checks. Two COMMs in one block can each see a funded purse, and the cap then decides. | Yes |

## Tests

- `rholang` `seal::tests::the_purse_is_the_owners_wallet_and_the_price_is_the_origins` and `a_membrane_is_one_owner_under_one_origin`.
- `rholang` `seal::tests::funding_is_scoped_and_spawned_tasks_keep_it`.
- `rholang` `comm_ledger::surface_tests::a_comm_is_one_cell_only_when_its_surfaces_share_a_membrane`.
- `models` `par_serde::tests::a_datum_without_a_seal_keeps_the_legacy_bytes` and `a_sealed_datum_round_trips_and_differs_from_the_unsealed_one`.
- `rholang` `seal_wiring_spec::inside_the_receivers_evaluator_a_transfer_from_the_senders_own_id_is_refused`. This is lane B's FX-13 check. Inside Alice's evaluator, Mallory's transfer from her own identifier fails, and no balance changes. The same transfer in Mallory's own run succeeds.
- `casper` `v6::surface::tests::a_stored_receive_is_funded_when_its_purse_less_the_blocks_holds_covers_one_cell`.
- `v6::region_spec::a_datum_stored_in_an_earlier_block_is_charged_to_its_sender`. Alice stores a datum at price 2. In a later block, Bob receives it. Alice's wallet pays one cell at price 2. Replay gives the same root and the same tally.
- `v6::region_spec::an_unfunded_stored_receive_is_not_a_match_candidate_in_play_or_replay`. A process wallet installs a service. The process wallet then pays the cell of a call. When the same block holds all that is left in the process wallet, the call does not match the service. Both blocks replay. A replay that gives the funded run's log with the held block's gate fails.

## Changed tests

- `gated_executor_spec::an_expired_grant_returns_its_funders_shares_in_play_and_replay`: the sponsor stores `@"grant-slot"!!(*slot)` in block 1. A later block peeks the datum, so the sponsor's wallet now pays that cell (decision 8). The test reads the charge from the settlement and asserts that it is one cell.
- The cross-host fixture (`casper/tests/fixtures/v6/cross_host`) is written again with `write_cross_host_fixture`. A datum under seal records now carries its record, so the produce hashes and the roots of v6 blocks change. Runs without seal records keep the legacy bytes, and the FX-2 golden root does not change.

## Open points

1. Decision 5 above (a `None` side and the client's record count two cells) needs a ruling if one cell is the intent.
2. The oracle reads the pre-state balance and the gate table. It does not see the surface draws of other runs in the same block. D76's cap at settlement still applies.
3. Lane A2 must accept `admits_waiting` as the hook point in the match coordinator.
4. A self-sealed envelope `{% P %}[# { P }]` passes `self_sealed_envelope` when P is `contract @"svc"(_) = { Nil }`. It does not pass when P is the `for` form, for example `for (_ <= @"svc") { Nil }`, `for (@x <= @"svc") { Nil }` or `for (_ <- @"svc") { Nil }`. The gate then refuses the envelope as `ForeignSignature`. The test uses the `contract` form. The `for` form needs a check by the owner of `hash_seal_admissible`.
