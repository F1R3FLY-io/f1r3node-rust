# Decisions — P0-09 (A3: floor-distance pacing and the deploy pool cap)

Each entry gives the decision, the alternatives, the reason and whether it is reversible.

## D-P0-09-1 — Cherry-pick d1c3a970f onto patch/P0-01

- **Decision:** `d1c3a970f` is applied with `-x`. Nine files had conflicts. All conflicts were formatting of Track A code that the earlier ports had changed, so the patch keeps the phase branch side (`--ours`) in those hunks.
- **Alternatives:** Port the hunks by hand.
- **Reason:** No conflict hunk contained A3 logic. The A3 logic merged without a conflict.
- **Reversible:** yes.

## D-P0-09-2 — Read the pending count without a lock

- **Decision:** `admit_deploy` calls `this.deploy_storage.pending_count()`. Track A called it through a mutex.
- **Alternatives:** None. dev `f1bc683d5` removed the mutex from the deploy storage.
- **Reason:** Prefer dev's code over ports.
- **Reversible:** yes.

## D-P0-09-3 — The two limits are configuration keys

- **Decision:** Track A hard-coded the backlog multiplier (64) and the pacing threshold (`MAX_FLOOR_DISTANCE_BLOCKS / 2`). The patch adds two `casper` keys with these defaults:
  - `deploy-pool-blocks-of-backlog = 64`. The pool cap is this value multiplied by `max-user-deploys-per-block`.
  - `proposal-pacing-floor-distance = 128`. A test keeps the default equal to half of the 256-block merge-scope backstop.
- **Alternatives:** Keep the constants.
- **Reason:** Caps and limits are configuration parameters with measured defaults. The defaults are Track A's values. The soak must confirm them.
- **Reversible:** yes.

## D-P0-09-4 — Pacing and the pool cap are node-local policy

- **Decision:** No escalation.
- **Reason:** Pacing changes only which deploys this node puts in its own proposals. Validators do not check it. The pool cap changes only which deploys this node accepts into its pool. Neither changes block validity, the state root or charging, so two nodes with different values stay in consensus.
- **Reversible:** yes.

## D-P0-09-5 — The pool cap check stays in admit_deploy here

- **Decision:** This patch checks the cap in `admit_deploy` before the insert. P0-10 moves the check under the rejected-buffer guard, so that the check and the insert are atomic.
- **Reason:** One patch for each Track A item. Until P0-10, concurrent admissions can exceed the cap by a small number of deploys. The cap is a soft limit, so this is acceptable for one patch.
- **Reversible:** yes.
