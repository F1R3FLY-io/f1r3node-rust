# P3-06 decisions: the throughput steps of Decision 60

Branch `patch/P3-06`, lane A2, cut from `patch/P2-13`. Decision 60 orders three steps and asks for a measurement after each one:

1. a runtime pool, with each runtime reset between envelopes
2. footprints from each run's event log on the record entry, so that the merge decides conflicts before it reads post-states (memo J, option 1)
3. a soft checkpoint per run.

All measurements are `v6::exit_spec::phase_timings_by_block_size` (release, 2 cores, one-sends, best of three). Run times are summed over the runs, which run two at a time.

## Step 1: the runtime pool

| # | Decision | Alternatives | Reason | Reversible |
|---|----------|--------------|--------|------------|
| 1 | `EnvelopeExecutor` keeps two pools of idle runtimes, one for play and one for replay. Each pool holds at most `workers` runtimes. A run takes a runtime from the pool, or spawns one if the pool is empty. It resets the runtime to the block pre-state, as before. After a successful checkpoint it returns the runtime to the pool. A run that fails drops its runtime. | One runtime per worker task. | `buffered(workers)` gives no worker identity. A pool bounded by `workers` reaches the same steady state. | Yes |
| 2 | Each run resets the runtime's COMM ledger. The cost, the storage rule (P2-16), the deploy data and the mergeable-channel set are already set again for each run (`charge_storage_left_in_space`, `process_deploy`, `evaluate`). | — | A pooled runtime must not carry state from the previous envelope. | Yes |

Test: `v6::exit_spec::pooled_runtimes_give_the_records_of_fresh_ones`. One executor runs block A, block B and block A again, from the same pre-state. The two runs of A have the same mid-root and post-root, gate, settlement, outcomes and phlo. Their user logs hold the same events. Both records replay on the pooled executor. A fresh host gives B the same post-root and settlement.

The order of events in a user log and in the close-block log can differ between two plays of the same block, with or without the pool. Parallel branches of a term record their events in the order in which they ran. Replay rigs the recorded order, so this does not affect validity. The test compares the logs as multisets.

The spawns are gone (1.50 s summed at 64 envelopes). The wall time of the runs falls only from 2.09 s to 1.65 s. ## Step 2: footprints on the record entry (memo J, option 1)

| # | Decision | Alternatives | Reason | Reversible |
|---|----------|--------------|--------|------------|
| 3 | A footprint is a sorted list of (channel hash, access) cells. It is a function of the run's event log, its mergeable number channels and the joins of the block pre-state. It does not read the run's post-state. New module `v6/footprint.rs`. | Keep the existing `EventLogIndex` rule, which needs the post-state. | The ruling asks for a decision before the post-states are read. | Yes |
| 4 | Five accesses. **Read**: a COMM with a persistent receiver from the pre-state (a contract call), a peek at a datum of the pre-state, or a persistent datum of the pre-state. **Append**: a datum that the run leaves in the space. **Write**: the run takes a datum or a linear receiver from the pre-state, or leaves a receiver in the space (on every channel of its join). **Join**: for a datum that the run leaves on a channel, the other channels of each join that the pre-state has on that channel. **Merge**: a mergeable number channel; it has no other access. Events that the run makes and destroys itself leave no cell. | Bernstein read and write sets only. | Two writes to a tuple space commute when both only add datums. Read and write sets alone would reject two sends to one queue, and the current rule accepts that. | Yes, before the first v6 block on a live shard. After that, a change is a protocol change. |
| 5 | Two runs conflict when they share a channel and some pair of their accesses on it clashes. Pairs that commute: Read with Read, Append or Join; Append with Append; Join with Join; Merge with Merge. Every other pair clashes. | Treat Read against Append as a clash. | A run that read a contract, or peeked a datum, saw the same state that it would see after another run added a datum. The serial order "reader, then appender" gives the merged state. | Yes, as in 4 |
| 6 | The merge takes the runs in envelope order. It drops a run whose footprint clashes with a kept run, as it already drops a run whose payer another kept run debited. Then it reads the post-states of the kept runs only, and merges them in one step. If that merge fails the single-value-cell check (two runs put a number on one channel that holds or receives one value), the merge falls back to the existing incremental trial merge over the kept runs. | Put the value type in the footprint. | The event log does not hold the data, so the footprint cannot see that a datum is a number. The fallback is the old algorithm and is deterministic. Play and replay take the same path. | Yes |
| 7 | The record entry holds the footprint as field 17 (`repeated FootprintCellProto`). Decoding rejects unsorted or repeated channels, channels that are not 32 bytes, unknown accesses, and Merge with another access. Failed, refused and exhausted runs have an empty footprint. | Recompute the footprints on replay and leave them out of the record. | The ruling puts them on the record entry. A light client or a scheduler can read the conflict decision without the post-states. | No: field 17 is part of the record encoding. |
| 8 | Replay recomputes each footprint from the recorded log and the pre-state, and the record is invalid if one differs. | Trust the recorded footprint. | The merge decision depends on the footprint, so a validator must not take it from the proposer. | Yes |

The fallback changes nothing for the other blocks. The rule "a datum on a channel of a pre-state join clashes with every other run" (`produces_touching_base_joins`) is replaced by the Join access, which clashes only with runs that touch the other channels of that join.

Tests: the unit tests in `v6::footprint` (each access, the full conflict relation, canonical decoding). `v6::exit_spec::footprints_let_commuting_runs_merge`: three sends of strings to one channel, two registry lookups, two receivers on different channels all complete. `v6::exit_spec::footprints_reject_runs_that_touch_the_same_cell`: a send after a receiver on the same channel conflicts, as does a second receiver, and two numbers on one channel conflict through the fallback. `v6::exit_spec::the_record_carries_each_run_footprint_and_replay_checks_it`: the footprints are on the record, they survive encoding, and a record with a forged footprint does not replay. `pooled_runtimes_give_the_records_of_fresh_ones` also compares the footprints of two plays.

At 64 envelopes the merge falls from 347 ms to 325 ms. A split of the merge (temporary timers, not committed) gives:

- footprints for 64 runs: 2.5 ms
- the post-state reads (`DeployChainIndex::new` for each kept run): 300 to 310 ms
- the single merge: about 15 ms.

The conflict decision is now about 1 % of the merge. All the one-sends are independent, so every run is kept and every post-state is still read. The post-state reads are 95 % of the merge, and step 3 removes them: with a soft checkpoint, the merge can take each run's changes from its hot store instead of a trie diff.

## Step 3: a soft checkpoint per run

| # | Decision | Alternatives | Reason | Reversible |
|---|----------|--------------|--------|------------|
| 9 | A run no longer calls `create_checkpoint`. After evaluation, the executor takes the run's hot-store changes (`HotStore::changes`), and then returns the runtime to the pool. A run has no trie root, so `EnvelopeRun` has no `post_root`. | `create_soft_checkpoint` and keep the snapshot. | The merge needs only the changed cells. `changes()` gives them in the form that a checkpoint would write, and no clone of the whole cache is necessary. | Yes |
| 10 | The merge computes each kept run's `StateChange` from the pre-state and a reader over the run's changes (`RunChanges`), which falls back to the pre-state for cells that the run did not touch. The datum and continuation binaries are encoded and sorted as the trie stores them. | Write the runs' changes to the trie and read them back, which is the old path. | No trie write per run and no read of a post-state. | Yes |
| 11 | rspace++: `StateChange::new` reads through a new trait `ChangeReader` (data binaries, continuation binaries, joins). The trie reader `RSpaceHistoryReaderImpl` implements it, so the existing callers do not change. | A copy of `StateChange::new` in the v6 module. | One state-change algorithm for the trie path and the run path. | Yes |
| 12 | Three tests read a run's post-state to show that the run moved no native balance before settlement: `gated_executor_spec` (two reads) and lane C's `region_spec` (one read). They now read the merged pre-settlement state (`mid_root`), where the same claim holds. | Keep a per-run root for tests only. | The claim is about the state before settlement, and `mid_root` is that state. | Yes |

Equivalence: the cross-host fixture was recorded before steps 2 and 3 (full checkpoint per run, the old conflict rule). Executed again with steps 2 and 3, it gives the same outcomes, mid-root, post-root, gate and settlement. Only the footprints are new. The fixture is then written again in the new record format (field 17), and `a_block_recorded_on_another_host_replays_here` passes on it.

### The next cost

The run wall time (673 ms) is about the summed setup (603 ms), so the setups of the two workers do not overlap. A split of setup (temporary timers, not committed) gives 9.5 ms for `RhoRuntime::reset` and less than 0.1 ms for everything else. `reset` makes a new hot store and calls `restore_installs`, which installs every system process again for each envelope.

A possible next step, which is not part of Decision 60: take one soft checkpoint at the block pre-state after the installs, and revert each pooled runtime to it in place of `reset`. If the revert is cheap, the estimate is about 1 ms per envelope for setup, eval and changes. On 2 cores, that would leave the merge and the settlement as the largest costs. This estimate is not measured.

## The full suite and a correction to P2-16

The first full suite on step 3 failed `footprints_let_commuting_runs_merge` with `ReplayCostMismatch`. `pooled_runtimes_give_the_records_of_fresh_ones` also failed sometimes in a loop. The fault was in P2-16: the storage charge depended on the interleaving of parallel branches. With the pool turned off, the failure stayed the same. P2-16.md, section "Correction", gives the cause and the fix. The fix is a separate commit on this branch. After it, ten loops of the four exit tests and the new `storage_charges_do_not_depend_on_the_interleaving` passed.

The scaling test `v6::exit_spec::scaling_by_worker_count` (ignored) is added for the Decision 61 run. `docs/rev-stacks/runbook-soak-and-scaling.md` is the runbook for the isolated-host soak and the 8- and 16-core scaling run.

A second worker adds nothing. The run wall time equals the summed setup with one worker and with two. `reset` costs about 18 ms per run at this pre-state (256 funded wallets), against 9.5 ms in the 64-envelope benchmark. It is 70 % of the execution time, and the setups of different workers do not overlap. Until `reset` changes, the 8- and 16-core run cannot reach η ≥ 0.6. The merge (about 4 ms per envelope) is the next sequential cost.
