# P2-04 decisions: the gate and the commitment table

Patch P2-04, "The gate and the commitment table", rev-stacks patch plan
r7.2, lane B. Branch `patch/P2-04`, cut from `patch/P2-02`. All code in this
patch is new. Nothing is ported. The code is in `casper/src/rust/v6/gate.rs`.

## Pending Q-18

The visible balance follows the proposed canonical settled form (Decision 9,
Q-18 open): a term that reads its own wallet sees the pre-state balance less
the commitments against that wallet up to and including its own gate
position. `GateOutcome::committed_through` and `GateOutcome::visible_balance`
give that value. If Q-18 goes the other way (revision 5: only the envelope's
own commitment), those two functions change. Nothing else changes.

## Decisions

| # | Decision | Alternatives | Reason | Reversible |
|---|----------|--------------|--------|------------|
| 1 | The gate is a pure pass over `GateInput`s in block order: `gate_block(reader, demand, inputs)`. It returns one `GateEntry` per envelope (delta, verdict, commitments) and the commitment table `C`. | A gate inside the executor. | The executor is lane A2's (P1-04, P2-05). The narrow interface that it calls is `gate_block` for play and `check_recorded` for replay. | Yes |
| 2 | Delta comes from a `Demand` seam. The only implementation now is `PhloLimitDemand` (delta = `phloLimit`). Q-24 (a static compute estimate) and `delta_sigma` (P3-01) become other implementations. A delta larger than `phloLimit` is refused. | Hard-code `phloLimit`. | Brief: leave a seam for both. | Yes |
| 3 | The wallet read is native, through `WalletReader`. `StoreReader::at(runtime_manager, pre_root)` resets a fresh runtime to the block pre-state and reads the hot store through P2-01's `RevStacks::balance`. The gate reads each wallet once per block and caches it. | An exploratory deploy. | Design §6.5: wallet reads are native, with no Rholang. | Yes |
| 4 | `need = delta × phloPrice`, with checked arithmetic. A negative `phloLimit` or `phloPrice` is `InvalidTerms`. An overflow is `Overflow`. A zero price admits with no commitment. The shard floor is P2-07. | Saturate. | No silent cut on a value that consensus checks. | Yes |
| 5 | `have = balance − C[w]`. Admit if and only if `have ≥ need` for every paying wallet. Only an admitted entry adds to `C`. A refused entry has no commitments. | — | Design §6.5. This gives the property that the sum of the commitments on a wallet never exceeds its balance. | — |
| 6 | Phase 2: the paying wallets are the deployer's wallet only (`GateInput::paying_wallets`). The gate loops over the paying wallets, so compound signatures (Decision 24: each component pays the full charge) need only a new `paying_wallets`. | — | Brief. | Yes |
| 7 | A signed term that names any signature other than the deployer's is refused (`ForeignSignature`). The names arrive in `GateInput.named`. `GateInput::from_deploy(deploy, named)` takes them from the caller. The annotation syntax (lane C, P2-18/P2-19) is not on the base, so the names are empty now. | Parse the term here. | The gate must not depend on the normalizer. See memo M-3. | Yes |
| 8 | Wallets are keyed in `C` by P2-01's `wallet_channel_id`. | Key by owner. | The channel id is the location of the stack, and it is what settlement debits. | Yes |
| 9 | Verdict and commitments go into the record as `Record.gate` (`RecordProto` field 11, `GateEntryProto`). A refused entry that carries commitments does not decode. | A separate record. | Brief: "the verdict and commitment go into the record". See memo M-2. | Yes, before any shard launches |
| 10 | Replay: `check_recorded` runs the gate again at the same pre-state and compares each entry with the record. Replay therefore rebuilds `C` from the record and refuses a record that does not match. | Trust the recorded verdicts. | Design §6.5: "Replay reproduces C from the gate verdicts in the record." | Yes |

## Outside the hotspot list (memo M-2)

`Record` lives in `v6/body.rs`, and lane A builds one in `v6/backend.rs`. The
patch adds the field `gate` (tag 11) to `RecordProto` and `Record`, an empty
list in `Record::empty`, and `gate: vec![]` in the one literal in `backend.rs`.

## Tests

- Unit tests in `v6::gate::tests`: later envelopes see earlier commitments; a foreign signature is refused; invalid terms and overflow are refused; a demand above the signed limit is refused; replay accepts the recorded entries and refuses a forged or short record; gate entries round-trip through the record wire format.
- Property test `commitments_never_exceed_a_balance` (proptest, random balances and envelopes): after every gate position the running sum of the commitments on each wallet is at most its balance, and it equals `committed_through`. An admitted entry commits exactly `phloLimit × phloPrice`. A refused entry commits nothing. The gate is deterministic, and its own entries replay.
- `casper/tests/v6/gate_spec.rs`: on a v6 genesis, the gate reads the native wallet at the pre-state, admits two envelopes, refuses the third with the exact `need` and `have`, refuses an unfunded payer with a non-zero price, and admits it at price 0. A second reader at the same root replays the entries.
