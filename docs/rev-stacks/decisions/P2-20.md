# P2-20 decisions: transfer history from the record

Patch P2-20, rev-stacks patch plan r7.2, lane B. Branch `patch/P2-20`, cut
from `patch/P2-10`. All code in this patch is new. Nothing is ported. The
code is in `casper/src/rust/v6/history.rs`.

## Scope of this round

This round gives the REV movements that the record holds: the COMM charges
(payer to proposer) and the compute charges (payer to compute wallet), per
envelope. It does not give user transfers made inside a run through
`rho:rev:wallet`. Those are native writes with no event log, the record does
not hold them, and memo M-6 shows that the merge drops them now. When M-6 is
decided, the user transfers join the history:

- with M-6 option (c), from the settlement rows in the record;
- with options (a) or (b), from a per-envelope transfer journal that the executor would add to the record.

The node's transaction API (`node/src/rust/web/transaction.rs`, `TransactionType`) is lane C's (P2-12). This patch gives that lane a source. It does not change the API.

| # | Decision | Alternatives | Reason | Reversible |
|---|----------|--------------|--------|------------|
| 1 | `history::transfers(record)` turns each recorded charge into at most two `RevTransfer`s: `CommCharge` to the proposer and `ComputeCharge` to the compute wallet, in record order. Charges of 0 give no transfer. | Read the post-state. | Design §6.13: the record carries the per-wallet amounts, so history needs no state read and no replay. | Yes |
| 2 | `history::wallet_history(records, wallet)` filters the transfers of a sequence of records by payer or payee. | — | A wallet's statement across blocks. | Yes |
| 3 | Wallets are named by their channel ids (`wallet_channel_id`), as in the record. Mapping an id back to a REV address is the API's job, because an id cannot be inverted (design P1). | Store addresses in the record. | Keeps the record small (P2-10, memo M-7). | Yes |

## Tests

- `casper/tests/v6/gated_executor_spec.rs::the_record_gives_the_block_s_rev_transfers`: a block of two charged envelopes is executed and its record decoded. The transfers add up to the debits, the COMM transfers to the proposer's credit (exact), and the compute transfers all go to the compute wallet. A payer's history sums to its debit, and the proposer's history has its two COMM credits.
