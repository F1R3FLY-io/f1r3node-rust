# P3-07 decisions: programmable tokens

Patch P3-07, "Programmable tokens", rev-stacks patch plan r7.10, lane C.
Branch `patch/P3-07`, cut from `patch/P3-03` (`1ba1c68cf`). All code is new.
The base needs only P2-19 (brief). It is cut from P3-03 so that the signer
rules of P3-02 and P3-03 are on it.

## Rulings used

- Decision 28 (Q-23): token creation is programmable. A token kind is named by
  an unforgeable name held by its issuer. REV's kind name is held by genesis
  alone. REV is the only staking token. Charges stay in REV. The conservation
  check covers REV only.
- Ruling of 2026-10-30 (question in this session): the kind of a stack is
  written as a **signed stack**, `{% s :: S %}[k]`.

## Decisions

| # | Decision | Alternatives | Reason | Reversible |
|---|----------|--------------|--------|------------|
| 1 | A signed term whose body is only token stacks is a stack of a kind when its signature, after substitution, is an unforgeable name `k` or the `bundle0` of one. The kind is the id of `k`. | A kind field in `CostStack`. | The ruling. No change to the parser or the model. | Yes |
| 2 | `{% s :: S %}[k]` with `k` itself is a **mint**: each cell deposits one unit of kind `k` on the wallet at its signature. `{% s :: S %}[bundle0{*k}]` is a **transfer** of one unit per cell from the writer's kind-`k` wallet. | Mint only when the writer is a stored issuer contract. | Holding the unforgeable `k` is the issuer's capability. An issuer publishes `bundle0{*k}` as the kind's public name: it identifies the kind and cannot be read, written or turned back into `k`. | Yes |
| 3 | The wallet of kind `k` for owner `o` is the native wallet of the owner `Unforgeable(Blake2b256("f1r3fly/token-kind/wallet/v1" ‖ len(k) ‖ k ‖ canonical(o)))` (`kind::kind_owner`). | A new variant of `WalletOwner`. | It reuses all native wallet operations (deposit, spend, balance, the per-wallet locks). The domain separation keeps kind wallets apart from REV wallets and from each other. | Until a shard holds tokens of a kind |
| 4 | REV has no kind name that a term can hold. A bare stack `s :: S` and a stack signed by a signer's signature are REV (P2-19, Decision 33). | An explicit REV kind name created at genesis. | Decision 28 needs only that no contract can mint REV. A kind stack writes only kind wallets, which are never REV wallets, so no term can mint REV. | Yes |
| 5 | A transfer of a kind checks the writer's kind balance first. If it cannot cover every cell, nothing moves and the term is a `ReduceError`. | — | Same rule as a REV stack (P2-19, decision 12). | Yes |
| 6 | The gate does not list the signature of a kind stack in `GateInput.named`. The static walk treats a stack body under a name that is not a known signer as a kind stack. If the name is not a kind at run time, the reducer applies the region rule and refuses it. | Treat it as foreign at the gate. | A kind name is a capability, not a payer. It pays no charge. The run-time check of P2-19 still refuses a non-signer region. | Yes |
| 7 | Charges stay in REV: a kind stack charges no compute of its own, and its COMMs, if any, are charged in REV as usual. | — | Decision 28. | Yes |
| 8 | Bonding refuses tokens of a kind by construction: bonds move REV through `rho:rev:wallet` and the SystemVault facade, which read and write REV wallets only. A kind wallet is never a REV wallet (decision 3). | A check in PoS. | No path from a kind wallet to a bond exists. The test `tokens_of_a_kind_never_pay_where_rev_is_required` shows that a holder of 5 units of a kind and no REV cannot pay 5 REV. A bonding test belongs with P2-11, when bonds move onto native REV stacks (Decision 32). | Yes |
| 9 | The per-block conservation check stays REV-only. Kind stacks do not change any REV wallet. | — | Decision 28. | Yes |
| 10 | `rho:rev:wallet` gets the read command `kindBalance` with `(kind, owner)`. The kind is `k` or `bundle0{*k}`. | — | A client or a contract can then read a kind balance. | Yes |
