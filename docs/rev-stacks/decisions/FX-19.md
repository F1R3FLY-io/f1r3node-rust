# FX-19 decisions (lane C): the declared per-firing bound

Branch `patch/FX-19`, cut from `patch/FX-17` at 0b01b1663. Design: Decisions 120, 124, 125 and 126. Memo: `docs/rev-stacks/memos/FX-19-declared-bound.md`. Names: u1…um deployers, d1…di deployments, B1…Bj blocks. W is a wallet.

## 0. Decision 132 (2026-11-06): a firing over its bound fails the enclosing run

Meredith ruled that any nested error causes the entire enclosing context to fail. A way to isolate a nested failure, so that the outer computation continues, is future work.

| Change | Detail |
|---|---|
| `dispatch.rs` | A firing that passes its bound returns `InterpreterError::FiringExhausted`, as any other error in stored code does. Before, the firing was dropped alone and the run continued. |
| `reduce.rs` | `aggregate_evaluator_errors` no longer filters out `FiringExhausted`, so the error reaches the run. |
| Charging, unchanged | The seal's owner pays the bound of the firing (`Firing::finish`). The deployment pays its own part: as for any evaluation error, its cost is its full phlo limit (`InterpreterImpl::handle_error`). |
| Effects | The run reverts to its soft checkpoint, so none of its effects stay, and the client's message does not stay either. The merge does not keep the run. |
| Replay | Replay requires the same failure and the same cost (`replay_deploy_e`), and the record's settlement must be equal. `close_charge_spec::replay_recomputes_the_cost_of_each_firing_and_rejects_a_changed_one` now covers a block whose run fails, and it still passes. |

**The buffer stays.** The run's effects are now discarded with the run, so the buffer is no longer necessary for that. It is still necessary for the charges to be deterministic:
- Without the buffer, a firing over its bound does some of its sends and receives before it passes the bound.
- Where the bound is passed depends on the order of evaluation, so play and replay can do different operations.
- Those operations can cause further firings, and the owners of those firings are charged.
- With the buffer, a firing over its bound does no operations. Its owner pays exactly the bound, and nothing else follows from it.

## 2. Decisions taken in the build

Ruled 2026-11-05: the first and third rows are Decision 129. Known issue 5 led to Decision 127: a firing limit for each seal. Lane B builds its syntax and its elaboration into `SealOrigin.phlo_limit` (field 4). This code reads that field unchanged.


| Decision | Alternatives | Reason | Reversible |
|---|---|---|---|
| The wallets that a firing holds are the purse of the stored continuation's seal and the owners that the stored body names statically (`region::resolved_owners`, which also resolves `# P` seals). Each holds the bound. | The purse and every signer of the installing deployment (the first draft) | A `# P` contract pays from its own wallet. ## 4. Known issues (Decision 88: not blocking)

1. **Small wallets in full blocks (Decision 125).** A run may hold free(W) / n. In a block with many envelopes, a contract with a small wallet is not fired. The datum and the receive both stay stored, as with Decision 79's filter. A later operation on the channel can match them.
2. **A seal bound at run time inside stored code.** A body that seals work with a name that it receives cannot name that wallet at match time. A charge to that wallet exhausts the firing (section 2). The run-time check of Decision 112 is unchanged.
3. **Ungated charges in a discarded firing.** Withdrawn by Decision 132: the whole run fails, and the client pays its own part as for any error.
4. **Bounds are held until the run ends.** A loop of N firings under one installer in one run holds N bounds. A long loop stops at free(W) / (n × bound) firings in one block and continues in a later block.
5. **Finding for Meredith: the bound is the installing deployment's whole phlo limit.** The installing deployment's `phloLimit` must cover its own run. The same number is then held for each later firing, and each reduction is a firing (Decision 124). Two tests had to change:
   - `forms_spec::work_that_stored_code_pays_for_does_not_count_against_the_clients_limit`: the stored code makes 13 nested reductions. With an install limit of 100,000, one hold already passes the installer's 100,000, so the code did not fire. The test now installs with a limit of 5,000.
   - `gated_executor_spec::a_user_transfer_and_bond_survive_play_and_replay`: the deployment's run needs more than 30,000 phlo, and its handle continuation fires in the close of the same block. The close holds the bound against the balance less the gate's commitment of the same limit. The test now uses 45,000 instead of 50,000.
   - A separate bound declared for each firing would remove this coupling, for example a field in the seal that defaults to the deployment's limit. Ruled by Decision 127, built by lane B (FX-21).
6. **Withdrawn (Decision 132):** a firing over its bound no longer consumes the client's message with no effect. The run fails and is discarded with the message.
7. **The hold is more than the payment by the COMM event storage.** Under the storage rule that the runs use, the COMM event storage of a firing is not charged. The hold of the stored side includes it, so a run holds 128 phlo more than it can pay for each firing. This is on the safe side.
8. **An error in stored code fails the client's run.** A received seal under a key that the installer did not sign is refused by the run-time check (Decision 112) before any charge, so Decision 129 does not apply. The refusal is an error of the evaluation, and the client's run fails, as it did before FX-19. Answered by Decision 132: every nested error fails the enclosing run, and a firing over its bound now does the same.
