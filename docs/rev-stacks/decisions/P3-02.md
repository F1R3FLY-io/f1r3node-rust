# P3-02 decisions: compound signatures, each component pays in full

Patch P3-02, "Compound signatures: each component pays in full", rev-stacks
patch plan r7.10, lane C. Branch `patch/P3-02`, cut from `patch/P2-19`
(`c21e91eab`). All code is new. `authority.rs` is not ported: the gate and the
settlement of P2-04 and P2-05 already loop over `GateInput::paying_wallets`,
so the per-component charge needs only the right set of wallets.

## Rulings used

- Decision 24 (Q-21): under `{% P %}[s1 (*) s2]` each component's wallet pays
  the full COMM and compute charge, a coordination cost. Weakening is
  forbidden: no component may be skipped.
- Decision 25 (Q-25): a joint wallet keyed by the compound itself pays once.
  That wallet is P3-03.
- Decision 26: the price floor is not scaled by the number of components.
- Ruling of 2026-10-30 (question in this session): the other components
  authorize by a **cosigned envelope**.
- Ruling of 2026-10-30: lane C may edit `casper/src/rust/v6/gate.rs` and
  `settle.rs` for P3-02. `settle.rs` needed no change.

## Decisions

| # | Decision | Alternatives | Reason | Reversible |
|---|----------|--------------|--------|------------|
| 1 | `DeployDataProto` gets `repeated DeployCosignature cosignatures = 15`, with `DeployCosignature { bytes cosigner = 1; bytes sig = 2; string sigAlgorithm = 3; }`. `DeployData` gets `cosignatures: Vec<Cosignature>`. | A separate envelope message. | One repeated field. A deploy without cosignatures encodes as before, so no deploy hash and no block hash changes. | Until a block stores a cosigned deploy |
| 2 | A cosigner signs the same preimage as the deployer: `DeployData::to_message()`, which leaves the cosignatures out, hashed by `Signed::signature_hash` for the cosigner's algorithm. | The cosigner signs the deployer's signature too. | Every signer signs one byte string, and cosignatures can be added in any order. The deploy term, price and limit are fixed by every signature. | Yes |
| 3 | The signers of a deployment are the deployer and every cosigner whose signature verifies. If any cosignature does not verify, the gate refuses the envelope as `InvalidTerms`. | Drop the bad cosignature and go on. | A bad cosignature is a malformed envelope. Dropping it would make the paying set depend on which signatures a node checks. | Yes |
| 4 | The normalizer environment injects `rho:system:cosignerId:<i>` for each verified cosigner, in the order of the cosignatures, with the cosigner's `GDeployerId`. A term names cosigner `i` with `new c(`rho:system:cosignerId:0`) in { ... }`. | A literal key in the signature syntax. | The same form as `rho:system:deployerId`, so the static resolution of P2-19 resolves it from the injections. | Yes |
| 5 | A signature in a signed term or a signed bind is admissible if it is a signer, or a compound whose every component is a signer (`region::admissible`). The gate and the reducer use the same rule. Any other signature is `ForeignSignature` at the gate and a `ReduceError` at run time. | — | Lifts the deployer-only rule of P2-19 for compounds of signers, as the brief says. A non-signer can still never be charged. | Yes |
| 6 | `GateInput::paying_wallets` is the deployer, then every component of every named signature, without repeats, in the canonical order of `WalletOwner`. The gate commits `Delta x phloPrice` against each, and refuses if any cannot cover it. Settlement debits each the full charge and credits the proposer and the compute wallet once per component. | Charge only the work inside each region. | The reducer meters an envelope, not a region (P2-05, P2-15). Each component consented to the whole envelope by cosigning it. When the signed term covers the whole deployment, which is the expected form, this equals Decision 24 exactly. When part of the term is outside the region, the components also pay for that part. The decision log of P3-03 or a later patch can narrow this when the meter counts per region. | Yes |
| 7 | A cosigner that no signed term names pays nothing. | Every cosigner pays. | Decision 24 charges the components of a signature. A cosignature only authorizes. | Yes |
| 8 | The payer of a `rho:rev:wallet` transfer must be a signer of the current deployment. | Accept any `GDeployerId`, as P2-03 did. | **Fixes a P2-03 defect.** P2-03 accepted any deployer id as the payer, so a deployer id stored on a public channel by one deployment could pay a transfer in another deployment. With cosigner ids in the environment this would also reach cosigners. The test `a_stored_deployer_id_cannot_pay_for_another_deployer` shows the fix. | No (security) |
| 9 | The price floor (P2-07) is unchanged. | Scale it by the number of components. | Decision 26. | Yes |

## Done-when

- "Each component wallet debited the full charge; conservation holds":
  `v6::region_spec::each_component_of_a_compound_pays_the_full_charge`. A
  deployment signed by alice and cosigned by carol runs
  `{% P %}[d (*) c]`. The gate commits against both wallets, settlement makes
  two equal charges, the proposer gets two COMM credits, the settlement is
  balanced, both settled balances fall by the full charge, and replay agrees.
- "Gate refuses if any component cannot cover":
  `v6::region_spec::the_gate_refuses_a_compound_that_a_component_cannot_cover_or_did_not_sign`
  (carol cannot cover; the same term without carol's cosignature is
  `ForeignSignature`; a tampered cosignature is `InvalidTerms`).
- Run time: `signed_region_spec::a_compound_of_signers_runs_and_a_compound_with_a_non_signer_is_refused`.
- Encoding: `casper_message::cosignature_tests`.

## Open items

1. **Clients.** The CLI and the web API cannot yet add a cosignature. A deploy
   with cosignatures arrives through the gRPC `DeployDataProto`, which carries
   them. A `node cosign` command is follow-up work.
2. **Per-region metering.** Decision 6 charges each component for the whole
   envelope.
3. **The v6 merge drops native REV writes** (P2-19, open item 3). Settlement
   runs after the merge, so the charges of this patch are not affected.
