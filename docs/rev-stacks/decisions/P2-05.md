## Memo M-5: the spend limit inside a run

Decision 9 fixes what a term sees when it reads its own wallet: the pre-state
balance less the commitments up to its own gate position. It does not say how
much a run may move out of the wallet. If that limit is the visible balance,
an earlier envelope can transfer away REV that a later envelope of the same
wallet has committed. Settlement then cannot take the later envelope's
charge, and conservation or the charge rule breaks.

- (a) Recommended, built: the spend limit inside a run keeps back all of the block's commitments on the wallet (`held`). The read shows `visible`. A term can therefore see slightly more than it can move.
- (b) Make the read equal to the spend limit (all of the block's commitments). This reverses Decision 9 for reads.
- (c) Settlement charges what is left. A short charge breaks Decision 14.

If (a) is wrong, a contract that reads its balance and then tries to move all of it gets a refusal where it expected success.

### Memo M-6: native transfers inside a run are lost at the merge

The v6 merge (P1-04, `merge.rs`) builds the merged state from each run's
event-log index. Native REV writes (P2-03) leave no event log, by design. A
run that transfers REV through `rho:rev:wallet` therefore merges as `true`,
but the transfer is not in the merged root. The test
`gated_executor_spec::a_run_cannot_spend_the_rev_its_block_has_committed`
shows it: Bob holds 6,000 at the run's post-root and 0 at the merged root.
No REV is created or destroyed, so conservation holds, but user transfers do
not happen.

- (a) Recommended: the merge takes each surviving run's native wallet changes from its post-root diff, for the wallet channels only. Two runs that both change one wallet's cells conflict, and the later one loses. This is lane A2's `merge.rs`.
- (b) Native operations write a synthetic event, so the existing merge sees them. This is lane C's native layer, and it reverses P2-03 decision 1.
- (c) Move native transfers out of the run: record them per envelope and apply them at settlement, in block order, like the charges. This is lane B's `settle.rs`, and it is the closest to design §6.7 ("one native debit … one native deposit").

The choice decides who owns the fix and where transfers are ordered. If it is
wrong, either transfers keep vanishing or two lanes fix it twice.
