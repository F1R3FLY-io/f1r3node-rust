# P3-05 decisions: sponsors and grants (funding slots)

Branch `patch/P3-05`, lane B, cut from `patch/P3-04` (8095c53b0).

## Scope

A funding slot is a signed term naming an unforgeable name (design r8, phase 3). A deploy obtains such a name only at run time, from a channel, so the gate cannot see a slot or commit against it before the run. Charging a deploy's work to a slot therefore needs region metering (Decision 49) and its admission pass before the merge (memo M-10). This patch builds the parts that do not depend on it: the authority over a slot, and grants with their window.

## Decisions

| # | Decision | Alternatives | Reason | Reversible |
|---|----------|--------------|--------|------------|
| 1 | A slot is the located stack at `WalletOwner::Unforgeable(id)` of an unforgeable name. `rho:rev:wallet transfer` accepts the slot's name as its payer (`(*slot, payee, amount)`), and presenting the name is the whole authority: no signer is needed. | Require the deployer to sign as well. | P10: holding the channel name is the authority. A term can present the name only if it holds it. | Yes |
| 2 | In the reducer's check of a signed term, a seal component that resolves to an unforgeable name is admitted, since the term holds that name. Components that name addresses still need the deployment's signers, and a `# P` component still needs the body to be P. | Keep refusing unforgeable seals (phase 2). | P10, and phase 3 of design r8. | Yes |
| 3 | The gate is unchanged: a seal on an unforgeable name is still an unresolved name statically, so a v6 envelope that names one is refused until region metering lands. | Admit the envelope and charge the deployer. | The deployer would pay for work sealed to the slot. | Superseded by region metering |
| 4 | A grant is the located stack at `Unforgeable(Blake2b256("f1r3fly/rev-stack/grant/v1" ‖ len(slot) ‖ slot ‖ opens ‖ closes))`. The window is part of the location, not separate state. | Store the window in a datum on the slot. | A run's direct state writes are dropped by the v6 merge (M-6), and the journal carries only moves. With the window in the location, every grant operation is an ordinary journaled move, and a window can never be changed after funding. | Until a shard holds a grant |
| 5 | `fundGrant (payer, (slot, opens, closes), amount)` moves REV from a signing payer to the grant. `drawGrant ((slot, opens, closes), payee, amount)` presents the slot's name and moves REV from the grant, only when the block number is in `[opens, closes]`. `grantBalance (slot, opens, closes)` reads the grant. | Let the gate check the window. | The window is checked inside the run against the block's number, which play and replay share. The gate cannot see a grant draw before the run (scope above). | Yes |
| 6 | The wallet process receives the block number from the runtime's block data. | — | Needed for decision 5. | Yes |
| 7 | Three of lane C's `signed_region_spec` tests asserted the phase-2 rule that an unforgeable seal is refused. They now assert that a held name runs, and use a ground name nobody signs for as the foreign case. `hash_seal_spec`'s compound test is changed the same way. | — | Decision 2. | Yes |

## Tests

- `grant::tests::a_grant_is_located_by_its_slot_and_its_window`, `a_grant_is_open_only_inside_its_window`.
- `rholang/tests/slot_spec.rs`:
  - `holding_a_slot_name_is_the_authority_to_draw_on_its_stack`: Alice funds a fresh slot with 500 and spends 200 from it to Bob by presenting its name.
  - `a_grant_is_drawn_only_inside_its_window`: a 10–20 grant of 300 refuses a draw at block 5, pays 100 at block 15, and refuses at block 25.
  - `a_term_sealed_with_a_slot_it_holds_runs`.
- `gated_executor_spec::a_grant_settles_draws_inside_its_window_in_play_and_replay`: a 2–5 grant funded in one block pays a draw at block 3 and moves nothing at block 9. Each block replays to the same settled root.
