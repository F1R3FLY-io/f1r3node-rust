## Merge fix: a run that adds a value to a cell of the pre-state (FX-2 log, observation 3)

**Finding (lane C, FX-2.md).** In a three-block run, a stored persistent receive whose body sends the same datum on each firing is not merged in the third block. The same happens with no seal syntax.

**Reproduction.** `contract @"c"(_) = { @"ran"!(1) }` in block 1, then `@"c"!(0)` in blocks 2 and 3. Block 3 records `Conflicted`. Block 2 leaves one number on `@"ran"`. In block 3 the run adds a second number. The merge applies `check_single_value_cell_not_overfilled` to every cell that a kept run adds to when the pre-state already holds data there. A lone run that adds a number to a cell that holds one number fails this check, so the merge drops the run's own post-state.

| # | Decision | Alternatives | Reason | Reversible |
|---|----------|--------------|--------|------------|
| 1 | The v6 merge applies the single-value-cell check only to a cell that two or more kept runs add to. | Keep dev's condition (the pre-state holds data, or two writers). | In v6 the footprints decide every conflict between runs (P3-06, decisions 3 to 6). Dev's condition also judges one run against the pre-state, and a run's own changes are a valid post-state. With two writers, the check stays the backstop for two numbers on a single-value cell. | Yes, before the first v6 block on a live shard. After that, a change is a protocol change. |

The change is in `merge_runs` (`v6/merge.rs`) only. Dev's merger for blocks (`conflict_set_merger`) does not change.

Test: `v6::exit_spec::a_stored_contract_that_sends_the_same_datum_on_each_firing_keeps_merging`. Five blocks: the contract, three single calls and a block with two calls. Every run completes, and every block replays. The two calls in block 5 add to a cell that already holds three values. That is not a single-value cell, so the two runs commute. The single-value case (an empty cell and two numbers) stays covered by `footprints_reject_runs_that_touch_the_same_cell`.

The seal variant of the finding needs FX-2's syntax. The test runs again with a sealed body after FX-8 merges FX-2.

## Decision 65: revert to a pre-state soft checkpoint in place of `reset`

| # | Decision | Alternatives | Reason | Reversible |
|---|----------|--------------|--------|------------|
| 2 | A pooled runtime keeps the soft checkpoint that it took right after its last full `reset`, with the root of that reset. A run at the same pre-state reverts to the checkpoint (`RhoRuntime::reset_to_soft_checkpoint`). A run at another pre-state does a full `reset` and takes a new checkpoint. | Keep `reset` for each run. | `reset` makes a new hot store and installs every system process again: 9.5 to 18 ms per run. The checkpoint's hot store is a persistent map, so a clone is cheap. | Yes |
| 3 | `reset_to_soft_checkpoint` reverts the space and then does the file part of `reset`: it seeds the file and directory descriptor counters from the root, clears the WAL and clears the snapshot stacks. That file part is now one private function (`reset_files`) that both paths call. | Revert the space only. | A pooled runtime must not carry file state from the previous envelope. The seed is a consensus commitment (PB-M-13), so both paths must compute it the same way. | Yes |
| 4 | Each envelope's run and replay is a spawned tokio task. The run state (runtime manager, pools, worker count) is in an `Arc<Runs>`. | `buffered(workers)` over futures in one task, as before. | Futures that `buffered` polls in one task interleave at await points but never run in parallel. Before this change, the runs of a block did not run in parallel at all (P1-04 to P3-06). | Yes |

Spawn time is now part of setup: the `spawn` column is always about zero.

Most of it is the per-run `StateChange` and the event-log index, which read the pre-state for each run, and those could run in parallel.
