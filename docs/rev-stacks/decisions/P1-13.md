# Decisions — P1-13 (offer status and receipts)

Each entry gives the decision, the alternatives, the reason and whether it is reversible.

## D-P1-13-1 — Base

- **Decision:** `patch/P1-13` starts at `patch/P1-04b` `afbdd44d0` (lane A2's rebase onto `patch/P1-rebased`), as Decision 34 directs.
- **Reason:** The receipts and the retained records need the record contract (`ExecutionRecord`) and the B3 block record, which arrive with P1-04b.
- **Reversible:** yes.

## D-P1-13-2 — An offer is a plain signed DeployData (Decision 34)

- **Decision:** Nothing from `4b160089b` is ported as code. That commit adds the costacc offered-funded admission path (`DeployEnvelope`, `OfferedFunded`, `cost_protocol_limits`, `owner_offer`, a separate envelope store). Under Decision 34, an offer is a plain signed `DeployData` in dev's pool, and dev's `deploy` path already admits it. What the patch keeps from `4b160089b` is the lifecycle that its spec tests: an offer is pending after admission and ordered after a block includes it.
- **Alternatives:** Port the envelope store and its admission without costacc types. That would duplicate dev's pool.
- **Reason:** The seam must not depend on costacc. One pool, one admission path.
- **Reversible:** yes.

## D-P1-13-3 — The deploy id is the deploy signature

- **Decision:** `offered_status` and the route take the deploy signature, hex-encoded and of any length, as `find_deploy` does. The source required a 32-byte `DeployIdV6`, which belongs to the costacc envelope.
- **Reason:** dev's pool, the B3 record entries (`envelope_id`) and the canonical-appearance index are all keyed by the signature.
- **Reversible:** yes.

## D-P1-13-4 — record_rejection: the interface for lane B's gate

Lane B wires the gate to call this after P1-13 lands. There are two entry points, and both remove the offer from the pool and record the rejection:

```rust
// casper/src/rust/v6/engine.rs, on V6Engine<R>
pub fn record_rejection(
    &self,
    deploy_sig: &[u8],          // the refused offer's signature (Signed<DeployData>::sig)
    pre_state_root: &StateHash, // the root the gate evaluated against (the attested root)
    block_number: i64,          // the number of the block being proposed
    reason: &str,               // the gate's cause, cut to offer-rejection-reason-bytes
) -> Result<bool, CasperError>  // true if the offer was in the pool and is now removed

// block-storage/src/rust/deploy/key_value_deploy_storage.rs, on KeyValueDeployStorage
pub fn record_rejection(&self, rejection: OfferRejection) -> Result<bool, KvStoreError>

// block-storage/src/rust/deploy/offer_rejection.rs
pub struct OfferRejection {
    pub deploy_id: ByteString,
    pub pre_state_root: Option<ByteString>,
    pub block_number: i64,
    pub reason: String,
}
```

- **Expected call site:** in `V6Engine`'s propose path, after the gate screens the selected envelopes. Call it once for each refused envelope, with `envelope.deploy.sig`, the attested root, `next_block_number` and the gate's cause. This is where `cdc23effd` called its `quarantine`.
- **Semantics:**
  - A second rejection of the same offer replaces the first.
  - `add` and `add_if_absent` on the pool clear the entry, so a resubmission through dev's `deploy` path reports `pending` again.
  - The log is in memory and is lost on restart.
- **Reversible:** yes. The signature is an interface between lanes, so a change needs lane B's agreement.

## D-P1-13-5 — Bounds are configuration

- **Decision:** Three new `casper` keys, with the source's values as defaults:
  - `v6-retained-records` = 1024: the number of fixed block records that `ExecutorCore` keeps. 0 keeps none.
  - `offer-rejection-log-capacity` = 4096: the number of offers in the rejection log. 0 turns the log off.
  - `offer-rejection-reason-bytes` = 1024: longer reasons are cut at a character boundary.
- **Wiring:** `CasperShardConf::v6_retained_records` goes to `V6Engine::new`, which takes it as a new last argument. The node sets the log bounds on the deploy storage at start-up.
- **Reversible:** yes.

## D-P1-13-6 — The receipt carries the B3 record fields

- **Decision:** `OfferedReceipt` holds the block hash, the outcome (`Completed`, `UserFailure` or `Conflicted`), `comm_phlo`, `compute_phlo` and the number of user-log events. The source's gate verdict, REV debits, fees and cost evidence are left out. They come from settlement and the gate, which are phase 2.
- **Reversible:** yes. Phase 2 can add fields to the receipt.

## D-P1-13-7 — Pool status reads the pool and the rejected-deploy buffer

- **Decision:** An offer in the pool or in dev's rejected-deploy buffer (merge-rejected and waiting for re-proposal) is `pending`. An offer that is in neither but is in the rejection log is `rejected`. Otherwise it is `unknown`. An offer with a canonical appearance in the DAG is:
  - `ordered` when no v6 engine is running, or when the engine has not executed the block yet
  - `executed` with a receipt when the engine retains the block's record
  - `notRetained` when the engine executed the block but no longer retains the record.
- **Reversible:** yes.
