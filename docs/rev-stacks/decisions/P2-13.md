## The M2 gate: CLI end to end (2026-11-01)

`scripts/v6/cli-end-to-end.sh` with a fresh data directory. It passes:

- The node logs "the approved block is protocol 6: this node runs the v6 executor".
- `wallet-balance` reads the genesis balance of the payer: 1,000,000,000.
- `node transfer --amount 7000 --phlo-price 1`, then four proposals: the payee holds 7,000. The payer paid 669 in charges.
- An overdraft (`--amount 2000000000`): the payee still holds 7,000. The deploy is charged and the transfer is refused.
- The proposer's wallet holds 2, one COMM phlo for each transfer.

### Against the r7 targets

| Target | Result |
|---|---|
| Settlement < 5 % of block time | Met at 64 envelopes (4.3 %). Not met at 1 to 16 envelopes (6.8 % to 13.7 %), where a fixed 30 ms settlement (one runtime at the merged root and one checkpoint) is divided over few envelopes. |
| Flat per envelope from 1 to 64 | Not met. Execution per envelope falls from 93 ms (1) to 42 ms (64), because the fixed gate, settlement and close-block costs are shared. From 16 to 64 it is flat (45 ms, 42 ms). |
| ≥ 150 one-sends per second on 2 cores | Not met: 24 per second without the close block, 23 with it. |
| Scaling η ≥ 0.6 on 8 and 16 cores | Not run (decision 6). |

### Why the throughput is a cost outside the model, not a missed target

The model prices an envelope by its evaluation. Evaluation is about 1 ms per one-send (67 ms for 64 envelopes). At 1 ms per envelope on 2 cores, the evaluation alone allows about 1,900 one-sends per second, so the modelled work meets the target.

The measured time per envelope is about 49 ms of CPU, summed over the two workers:

- **Runtime spawn: 23 ms.** `RuntimeManager::spawn_runtime` builds a new runtime for each envelope (P1-04 decision: one session for each envelope from the block pre-state). Alone it costs 6.4 ms. With two workers it costs 23 ms, so the spawns contend for a lock.
- **Setup: 9 ms.** Reset to the pre-state, the reservations and the journal marker are writes to the hot store.
- **Checkpoint: 15 ms.** A full `create_checkpoint` for each run, so that the merge has a post-root.
- **Merge: 5.6 ms per envelope.** `merge_runs` reads each run's post-state.
- **Close block: about 145 ms per block.** This is dev's close-block system deploy (the PoS epoch work in Rholang). It does not depend on the number of envelopes, and it is outside the per-envelope model.

The model does not include the session lifecycle: a runtime per envelope and a full checkpoint per run. The design's 160 to 280 per second assumes that this lifecycle is cheap compared with evaluation. On this code it is about 48 times the evaluation. The steps that could close the gap are outside this patch, and a ruling decides between them:

1. A pool of runtimes for each worker, reset between envelopes instead of spawned.
2. A soft checkpoint for each run, if the merge can use the run's event log and its number-channel data without a trie root.
3. A merge that does not read every post-state.

With 1 and 2, the measured costs suggest about 10 ms per envelope, or about 200 per second on 2 cores. That estimate is not measured.
