## Tests

- `casper/tests/v6/forms_spec.rs`: one test for each elaborated form, and each sugar case elaborated and compared with its form. Every block replays to the same settled root and settlement.
  - `the_two_party_form_charges_each_surface_and_the_installer_for_its_continuation`: Bob installs `{% for (_ <- @"x") { {% P %}[d] } %}[d]` at price 1. Alice sends `{% @"x"!(1) %}[d]` at price 2. Bob's surface pays two cells (the receive and the COMM inside P), plus P's work, at price 1. Alice pays one cell at price 2. The implicit-seal sugar (`for (_ <- @"x") { P }` and `@"x"!(1)`) has the same shape.
  - `the_one_party_form_pays_once_for_a_redex_under_one_seal`: `{% for (_ <- @"x") { P } | @"x"!(1) %}[d]` pays one cell for each redex, and there is no surface charge. The bare sugar has the same shape.
  - `the_lollipop_charges_the_comm_to_s1_and_the_continuation_to_s2`: `{% for (_ <- @"x") { P } %}[d -o c] | @"x"!(1)` charges the COMM on x to d, and P's COMM and work to c. The explicit layers `{% for (_ <- @"x") { {% P %}[c] } %}[d]` have the same shape.
  - `separately_named_regions_pay_only_their_own_work` (D5): `{% P %}[d] | {% P | P %}[c]` charges one cell to d and two to c.
  - The compound and `# P` sugar cases are covered by the existing tests. `region_spec::each_component_of_a_compound_pays_the_full_charge` covers each component paying in full (Decision 24), with the deployer also paying the top level. `a_funded_joint_wallet_pays_once_for_its_compound` covers a funded joint wallet paying once. `gated_executor_spec::a_stack_in_a_self_sealed_region_draws_on_the_funders_shares_pro_rata` covers a `# P` region drawing on its funders.
- `region_spec::data_sent_to_an_owners_contract_runs_under_the_owners_membrane_and_is_paid_there` (lane C's test, from FX-13) now asserts that the owner's surface charge has work, and that the sender's work and the owner's work add up to the run's work.
- `region_spec::a_fired_continuation_draws_on_its_author_not_on_the_firing_region` asserts the installer's surface charge: one cell at price 1.
- Changed by D7 and D4:

The bonder's wallet pays that work, and the compute wallet gains the envelope's compute credit plus exactly that charge. The block replays. `gated_executor_spec::a_user_transfer_and_bond_survive_play_and_replay` and two other `pos_bond_admin_spec` tests now include the close charge in their exact balances.

## The client's phlo limit (plan r8.12)

| # | Decision | Alternatives | Reason | Reversible |
|---|----------|--------------|--------|------------|
| 9 | `CostManager` has an own origin, set by the executor to the envelope's signature for each play and replay run, and cleared when the runtime goes back to the pool. A charge under a record whose origin is another envelope is still recorded in the work tally, but it does not use up the run's phlo limit. With no own origin set (legacy runtimes, system deploys), every charge uses up the limit as before. | Count every charge (before). Give stored code its own limit. | Plan r8.12: the phlo limit counts only the client's own surfaces. Stored code pays its own work from its own wallet (Decision 75), so that work must not exhaust the client. `processed.cost`, and so `run.compute_phlo` and the `Exhausted` test, now hold the client's own work only. This also settles the second half of F38. | Yes |
| 10 | Foreign work in a run has its own bound: `FOREIGN_WORK_BUDGET`, the default block demand cap (about 5.8 million phlo). A run whose foreign work passes the bound stops with `OutOfPhlogistons`, and the run is `Exhausted`. The client still pays only its own part. | No bound. A bound equal to the client's limit. A bound from the owner's balance. | Without a bound, a stored continuation that does not stop would run without limit on every validator, because the client's limit no longer counts its work. A block can never demand more work than its demand cap, so one run's foreign work needs no larger bound. A bound from the owner's balance needs the D79 funding oracle, which is not on this branch. | Yes |

Tests: `own_limit_tests::only_the_clients_own_work_uses_up_its_limit_and_foreign_work_has_its_own_bound` (unit test of the two meters, and of the legacy runtime with no own origin), and `forms_spec::work_that_stored_code_pays_for_does_not_count_against_the_clients_limit`.

New finding, found and fixed here (Decision 88): **blocking.** The first version of decision 9, without decision 10, let a stored continuation that never stops run without limit inside a client's run. That is a safety finding of High severity (the validators stall). Decision 10 closes it. The bound is reversible and can become the owner's spendable balance when the D79 oracle is merged.

For `forms_spec`: Bob installs a continuation of 40 nested COMMs. Alice fires it with a limit of 1,000. Bob's surface pays more than 1,000 in work, Alice's run is not exhausted, and her charge and her run's meter stay within 1,000. With the limit counting every charge, Alice's run is exhausted at 1,000.
