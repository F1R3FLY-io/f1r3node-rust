## Correction (2026-11-01, found in P3-06): the charge depended on the interleaving

**Finding.** The full suite on `patch/P3-06` failed `footprints_let_commuting_runs_merge` with `ReplayCostMismatch`. The cause is in this patch, not in P3-06. A play of `new x in { contract x(@n) = { Nil } | x!(1) | x!(2) }` cost 378 or 484 phlo. Its replay always cost 378, so about 4 plays in 10 did not replay. Without the runtime pool, the failure stayed the same.

**Cause.** Parallel branches of one term run at the same time. A send stores its datum in the space, and only then records the datum as the run's own (`stored_datum`). A receive in another branch can take the datum in that gap. `removed_datum` does not find the datum, so the receive treats it as a pre-state datum and refunds nothing. The send then charges event storage and records a datum that is no longer in the space. The run pays 106 phlo (produce storage 42, event storage 64) for nothing that it left. A receive matched by a concurrent send before it records its continuation has the same gap.

| 9 | `removed_continuation` records a miss, as `removed_datum` already does. The storing branch checks for a miss and records the item in one step under the rule's lock (`left_datum`, `left_continuation`). If another branch took the item first, the storing branch refunds the item's storage and does not charge event storage. | Hold the rule's lock across the space operation. | The net charge for an item is then the same in every interleaving: zero when the item does not stay. The space operation keeps its own locks, and the rule's lock covers only the bookkeeping. | Yes |

The rule itself does not change. A run pays for what it leaves in the space. Only the bookkeeping now gives the same result in every order.

The block holds a contract with two calls, a race of two receivers for two sends, and a persistent receiver with three sends. Each envelope has one charge over the 30 plays, and every record replays.
