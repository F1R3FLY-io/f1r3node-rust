**Known issue, for the order-floor commit:** the deploy lifecycle marks the envelopes of every finalized block as included. Under P11 a void block can be finalized. The lifecycle must skip void records, or it releases the envelopes that the engine put back.

## 4. Decision 109: `AlreadyIncluded` and the network-wide refusal

| Decision | Alternatives | Reason | Reversible |
|---|---|---|---|
| The gate has two new refusals, `AlreadyIncluded` (verdict 5) and `Discarded` (verdict 6). A refused envelope gets delta 0, is not run, and is not charged. The gate checks them before any other rule. | A separate pass before the gate | The gate record already carries every refusal, and replay checks it entry by entry | Yes |
| The core derives a status for each envelope from canonical records: `Included` when a normal record ran it (any outcome except `NotRun` and `Voided`); `Discarded` for every envelope of a (d) record and for the unreadable envelopes of a (c) record. (a) and (b) give no status. | Count `NotRun` as included | A gate refusal did not run or charge the envelope, so a later carrier may run it | Yes |
| The statuses are written in the same LMDB put as the record (key `e` + signature), so they survive a restart and do not depend on record retention | Rebuild from retained records | Retention is a node setting, and a status must not differ between nodes | Yes |
| The prior of a target is the status of each of its envelopes from the store and from the speculative records ahead of it, kept only if the carrier's block number n satisfies n < target and n + `deploy_lifespan` > target | Positions instead of block numbers | Acceptance already refuses an envelope outside the lifespan (`transaction_expiration`), so an older status can never apply. The window makes the rule independent of what a node has pruned. | Yes |
| `deploy_lifespan` comes from the on-chain shard configuration (`CoreParams::deploy_lifespan`) | — | It is a consensus value | — |
| Play and replay take the prior through `ExecutionBackend::execute_after` and `replay_after`. `execute` and `replay` keep their signatures and use an empty prior, so existing tests do not change. | Change the trait signatures | Less churn | Yes |
| `Validate::repeat_deploy` accepts every v6 block. The repeat rule for v6 is the gate's `AlreadyIncluded` at execution. | Keep both | Q-33 section 6: acceptance cannot see whether the earlier carrier is void | Yes |

**Known issue, not blocking:** the statuses are not pruned. Each entry is 9 bytes plus the signature. Pruning can remove entries whose block number plus the lifespan is below the canonical frontier's block number. It is safe because the decision applies the window itself.

**Known issue, for the order-floor commit:** the inclusion screen at the proposer's attested root does not yet use the statuses (Q-33 section 6, "Inclusion check").
