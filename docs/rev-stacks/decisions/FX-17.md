## 3. Void records (Q-33 revision 3, Q-34)

| Decision | Alternatives | Reason | Reversible |
|---|---|---|---|
| The predicate checks (b), then (c), then (a), from the block and the pre-state only. (d) is decided after the runs. | Another order | One order makes the reason a function of the block and the pre-state | Yes |
| A void record for (a), (b) or (c) has post = mid = pre, one `Voided` entry for each envelope, no gate, no settlement and no close. Record field 13 holds the reason. | A separate record type | The record format grows by one field. Old records decode with reason 0, which is no void. | Yes |
| A (d) record keeps the runs' entries, gate and settlement, sets post = pre and drops the close. Replay runs the deployments and then the close in play mode, and accepts only if the close fails with `UnexpectedSystemErrors` or `ConsumeFailed`. | Mark the entries `Voided` | Replay needs the entries' logs to run the deployments again | Yes |
| Replay rejects a void record for a valid block and a normal record for a void block, in both directions | — | Q-33 section 4 | — |
| A fixed void record is evidence `Offence::VoidBlock { reason }`, with `slashable()` true only for (b) and (c). The count for each proposer and reason is written in the same LMDB put as the record. It survives restart. Metric `v6.void-blocks{reason}`. | Count in memory only | Q-34: persisted with the canonical records | Yes |
| At a fixed void record the engine puts the envelopes of (a) and (b) back in the pool and clears their rejection entries. It removes the unreadable envelopes of (c) and every envelope of (d), and records a rejection for each. | — | Q-34 | Yes |

**Defect found and fixed:** a close whose result never arrived (`ConsumeFailed`) panicked in play, because `dev`'s diagnostic called `check_replay_data` on a play runtime. The diagnostic now runs only on a replay runtime (`RhoRuntimeImpl::is_replay`).

**Known issue, not blocking:** a (d) close is replayed in play mode, because the record has no close log. If a close failure depended on the order of play (Decision 89), two nodes could disagree on (d). The test reaches (d) only with an empty pre-state.

**Known issue, for the order-floor commit:** the deploy lifecycle marks the envelopes of every finalized block as included. Under P11 a void block can be finalized. The lifecycle must skip void records, or it releases the envelopes that the engine put back.

Tests: `close_charge_spec` reasons (a) to (d), both replay directions; `core` and `store` tests for evidence and counts; `evidence` round trip and the slashable flag.
