**Defect found and fixed:** a close whose result never arrived (`ConsumeFailed`) panicked in play, because `dev`'s diagnostic called `check_replay_data` on a play runtime. The diagnostic now runs only on a replay runtime (`RhoRuntimeImpl::is_replay`).

**Revised (2026-11-04, Meredith):** the failed close is part of the trace. Replay follows the trace and does not decide (d) again.
- In a gated close (`SystemGate`, so only the v6 executor), a platform failure of the close (`UnexpectedSystemErrors`, `ConsumeFailed`) no longer ends play with an error. Play takes the event log up to the failure and records the close as `ProcessedSystemDeploy::Failed { event_list, error_msg }`, with `error_msg = "close failed: " + the failure`. The close's refusal events are appended to that event list as for a close that runs.
- A (d) record carries exactly this one failed close. Its post-root is the pre-root, and its entries, gate and settlement are those of the runs.
- Replay rigs the recorded event list, runs the close, and accepts only if the close fails with the same message and the rigged trace is consumed (`check_replay_data`). The close's membrane meter replays from the recorded refusals.
- Test: `close_charge_spec::a_failed_close_is_part_of_the_trace_and_replay_checks_it`. The unaltered trace replays, and a different failure message is rejected. As for every deploy, replay checks the trace's COMMs; a produce or consume that took part in no COMM is not checked.

**Deploy lifecycle (fixed in the order-floor commit):** `block_facts` counts as applied only the envelopes that the canonical record ran. When a record is fixed, the core registers the envelopes that it did not run (every envelope of a void record, and each `NotRun` entry, `AlreadyIncluded` included) and evicts the block's cached facts. On start the engine registers again from the retained records above the LFB. The registry is process-wide and keyed by block hash. That is safe because the canonical record is consensus data, so every node in the process registers the same set.

Tests: `close_charge_spec` reasons (a) to (d), both replay directions; `core` and `store` tests for evidence and counts; `evidence` round trip and the slashable flag.

Tests: `core` P5 at 1/3, 2/3 and more than 2/3; a newer block of a validator replaces its older attestation and not the reverse; a misattesting validator supports nothing; a rebuilt tally in another order gives the same p*. Storage: `the_order_floor_moves_on_its_own_and_bounds_the_lfb` (crash ordering: the order is written first, and the LFB can never pass it).

**Findings from the end-to-end test:**
- The proposer's own attestation must count. `create_block` now adds it to the tally. Without it, each of three equal validators sees only two thirds of the stake, and the LFB never moves.
- P5 needs more than 2/3 of the bonded stake to execute and attest. The default test genesis bonds 4 validators with stakes 1, 3, 5 and 7, and the 3-node tests run only the first three (9 of 16). Under P11 their LFB stays at genesis while the order floor moves. `driven_engines_advance_only_when_the_test_ticks_them` and the lag-gate test now check the order floor, and `the_lfb_follows_the_attested_canonical_roots_below_the_order_floor` uses a 3-validator genesis.
