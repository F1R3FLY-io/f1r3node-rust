# FX-14 decisions: a PoS bond takes a bond receipt (Decision 82)

Branch `patch/FX-14`, lane B, cut from `patch/FX-12` (435568f9d). This closes F35, the bond hijack in FX-11's open item 2: a third party with a validator's published deployer id could register a pending bond for that validator and get its handle.

| # | Decision | Alternatives | Reason | Reversible |
|---|----------|--------------|--------|------------|
| 1 | A successful `rho:rev:bond` `bond` answers `(true, receipt)`. The receipt is an unforgeable name whose identifier is `"f1r3fly/rev-stack/bond-receipt/v1" ‖ pk ‖ Blake2b256(random state of the call)`. | A random name, with a stored map from receipts to keys. | A term cannot write an unforgeable name, so only the bond process can make a receipt. The bond process makes one only for a bonder who holds the enclosing seal (FX-7). The key is in the identifier, so the receipt needs no state. A run's direct state writes are not kept (M-6), and the journal carries only moves. The call's random state makes the receipt the same in play and replay. | Yes |
| 2 | `rho:rev:bondAdmin` `receipt` answers `(true, pk)` for a receipt and `(false, "expected a bond receipt from rho:rev:bond")` for anything else. | Put the read on `rho:rev:bond`. | Only PoS needs the read, and PoS holds the admin name. | Yes |
| 3 | `PoS!("bond", receipt, amount, returnCh, handleCh)` takes the receipt instead of a deployer id. It reads the key through `receipt`, and a refusal goes to `returnCh`. PoSV6's `getUser` helper is removed, so no PoS entry point reads a deployer id any longer. | — | Decision 82. | Yes |
| 4 | A receipt is not spent when PoS uses it. | Record spent receipts. | Using a receipt again gives its own holder a second registration. Each registration still passes the native-bond check at the close (Decision 72). | Yes |

## Tooling and docs

- `native::bond_term` passes the receipt to PoS.
- `rholang/examples/bond/bond.rho` does the same.

## Tests

- `rev_bond_spec::a_deployer_bonds_its_own_rev_natively`: the answer is a receipt whose key is the bonder's, and a value that is not a receipt has no key.
- `pos_bond_admin_spec::a_published_deployer_id_does_not_act_for_its_validator`: Mallory also calls `PoS!("bond")` with Alice's published deployer id. She is refused with "expected a bond receipt from rho:rev:bond", and the close sends her no handle.
- `pos_bond_admin_spec::a_pending_bond_backed_only_by_a_withdrawn_bond_is_dropped`: the new registration uses a receipt from a native bond of 1. The pending bond of 1,000 is dropped, and the 1 is released back to the wallet.
- `genesis_contracts_records_spec`: `PoS!("bond")` with a deployer id is refused.
- `gated_executor_spec::a_user_transfer_and_bond_survive_play_and_replay` and the other `pos_bond_admin_spec` tests use the receipt.
- `term_builders_accept_only_valid_addresses_and_amounts` checks that `bond_term` passes the receipt.

## Follow-ups (plan r8.12): spend on use, custody at the validator's seal, genesis handles

Decision 4 above is reversed: a receipt is now spent on its first use.

| # | Decision | Alternatives | Reason | Reversible |
|---|----------|--------------|--------|------------|
| 5 | PoS keeps a set `spentReceipts` in its state. `bond` refuses a spent receipt with "This bond receipt is already spent.", and adds the receipt to the set when it records the pending bond. | Bind the receipt to the bonding deploy. | Only the code that moved the REV can register, and only once (revision 12 note on Decision 82). PoS state is kept across runs, and the native layer's direct writes are not. | Yes |
| 6 | A validator's handle is the unforgeable name `"f1r3fly/rev-stack/validator-handle/v1" ‖ pk`. Only the native processes make it. `rho:rev:bond` `handle (deployerId)` answers `(true, handle)` only to code that holds the validator's enclosing seal (FX-7). `rho:rev:bondAdmin` `handleKey (handle)` gives the key, and `handleOf (pk)` gives the handle. | A custody contract that checks a signature (memo option A). A fresh handle per bond, held in PoS state. | Custody is at the validator's seal: any later deploy of the validator takes the handle again at its own seal, and a published deployer id gives nothing. The handle needs no state. | Yes |
| 7 | PoS no longer keeps a `handles` map. `withdraw`, `commitRandomImage` and `revealRandom` read the key through `handleKey`. The close sends `handleOf (pk)` on the bonding deploy's handle channel. | — | One rule for every holder of a handle. | Yes |
| 8 | A genesis validator takes its handle at its own seal, in the same way. | A genesis claim step. | Genesis has no bonding deploy. The handle depends only on the key, so genesis needs no change. | Yes |
| 9 | `native::withdraw_term` takes the handle at the deployer's seal and withdraws with it. | — | Tooling for a validator's later deploy. | Yes |

### Tests

- `rev_bond_spec::a_validator_takes_its_handle_only_at_its_own_seal`: Alice takes her handle, and its key is hers. Mallory, who holds Alice's published deployer id, is refused.
- `pos_bond_admin_spec::a_bond_receipt_is_spent_by_its_first_registration`: one receipt registers 500. The second use is refused, gets no handle, and does not change the bond.
- `pos_bond_admin_spec::a_genesis_validator_takes_its_handle_at_its_own_seal`: a genesis validator commits and reveals with the handle it takes at its own seal.
- `pos_bond_admin_spec::a_published_deployer_id_does_not_act_for_its_validator` adds Mallory's `handle` call with Alice's id, which is refused. The test helper `with_handle` now takes the handle at the deployer's seal instead of from a test channel.
- `two_pos_bonds_on_one_native_bond_admit_the_first_and_release_the_rest` now uses two receipts, from native bonds of 1,000 and 500.
- The spec's envelope limit is 200,000, because the impersonation deploy now makes five calls.

### Known issues (Decision 88)

1. **A handle cannot be revoked.** It is the same for the whole life of a key. Code that the validator passes its handle to can act for the validator until the key is retired. Known issue, not blocking: the validator must choose to pass the handle on, so this is not an authority defect of High severity, and r12 §6.3 does not cover handles.
2. **`spentReceipts` grows without bound.** Known issue, not blocking: this is storage growth, not an authority or §6.3 matter.
