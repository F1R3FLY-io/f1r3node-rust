## 2. Decisions

1. **The seal format.** The stored record is lane C's: `SealOrigin.phlo_limit` (field 4) carries the limit, and FX-19 reads it unchanged. The term carries `CostSignedTerm.seal = ElaboratedSeal { kind = 1, origin = 2, phlo_limit = 3 }`. `origin` is a 32-byte Blake2b256 digest of the envelope, the price and the signers (`seal::origin_digest`), not the whole `SealOrigin`. Reason: a whole origin in every continuation seal cost about 160 phlo for each stored continuation. Revision 2 of the memo proposed `SealRecordProto` field 5. Decision 127 replaced it.
2. **The limit.** A seal carries its declared limit (`; n`). A seal without one carries the deployment's `phloLimit`. A continuation that the pass seals is the enclosing seal, so it carries the enclosing seal's limit. A compound made from a nested region carries the smaller of the two limits.
3. **The pass is an AST pass before normalization** (`cost_accounting::elaborate`). It wraps the deployment in the deployment seal and seals every unsealed continuation at every depth: `for`, `contract`, and the process positions of `|`, `new`, `let`, `match` and `if`. It does not enter data: send arguments, quoted names and bundles stay as written. Lollipop and compound keep their existing rewrites.
4. **A `# P` region is not entered.** Its body must stay P, because the hash names P. Its continuations take their seal from the reducer's defaulting, as before.
5. **A binder that rebinds a name that its seal uses is refused** at compile time. The pass copies the seal's syntax into the continuation, so a rebound name would change the seal's meaning.
6. **The deployment seal cannot be written in source.** The pass writes it with an identifier that the parser cannot produce. The normalizer resolves it to the deployer's `GDeployerId`.
7. **Which code is elaborated.** Every evaluation that sets deploy data first (user and exploratory deployments through `RuntimeOps::evaluate`) is elaborated when seal records are on. System deployments do not set deploy data and are not elaborated (Decisions 81, 94, 119). A one-shot flag in the reducer carries the request, so stale deploy data cannot elaborate a system deployment.
8. **Seals in the reducer.** The reducer takes kind, origin and limit from the term. The record of the running code still supplies the origin to compare with. The owner check (signed or held) is unchanged.
9. **Two origins are the same when envelope, signers and price agree.** The limit is not part of the comparison. `shares_membrane` changes with it, so two seals of one owner and one origin with different limits are still one membrane and pay one cell (Decision 80). This changes lane C's `shares_membrane`.
10. **A `# P` seal is not checked against the origin.** Its authority is P itself. It runs under the origin of the code that evaluates it, as before.
11. **The two copies when a receive is stored.** The stored record's origin must have the digest of the continuation's term seal. The stored record then takes the continuation seal's limit, so FX-19's bound is the limit of the seal that the firing runs under. A stack body and a `# P` continuation are not compared.
12. **A seal written in data keeps its writer's origin.** A sealed term that u2 writes and u1's code runs is refused, because its origin is not the running code's. Before, the seal was checked against the running origin's signers (Decision 77 as built). This is the rule of Decisions 52, 53 and 63 (a seal verifies against the envelope that wrote it), which the term now makes checkable. **Question for Meredith:** confirm the writer-origin reading, or keep the running-origin reading for received data. The second reading drops lane A1's origin check for received processes.

## 2a. Cost of elaboration (finding for Meredith)

Elaboration makes every continuation a sealed term, and a stored continuation is charged by its size. `elaboration_spec::measure_the_cost_of_elaboration` (ignored, a measurement):

| Term | Bytes, plain → elaborated | Phlo, plain → elaborated |
|---|---|---|
| `@"x"!(1)` | 15 → 137 | 101 → 101 |
| One COMM (one stored continuation) | 70 → 317 | 442 → 563 (+27%) |
| Two COMMs | 141 → 513 | 899 → 1,142 (+27%) |

With the whole origin in the term the same rows were 601 and 1,217 phlo. Most of the rest is the deployment seal's signature, the deployer's 65-byte key, repeated in each continuation. **Known issue, flagged:** about 120 phlo more for each stored continuation. Deployments with tight limits must raise them. A smaller signature for the deployment seal (one reference instead of the key) would remove most of it. That is a format change for Meredith.

## 4. `forms_spec` as a normalizer test

## 5. Changed expectations

- `forms_spec::work_that_stored_code_pays_for_does_not_count_against_the_clients_limit`: FX-19 known issue 5 coupled the bound to the install limit (5,000). The install now has a limit of 100,000, and the region declares its firing bound: `[d ; 20000]` (Decision 127). An install limit of 5,000 no longer covers the elaborated 13-level term.
- `region_spec::data_sent_to_an_owners_contract_runs_under_the_owners_membrane_and_is_paid_there` is ignored. u2 sends `{% stack %}[a]` (a is u1's identity) to u1's contract. It now carries u2's origin and is refused (decision 12). It awaits the ruling below.

- `seal_record_spec` route tests, payload "owner seal" (decision 12): u2 writes `{% slot :: () %}[a]` with u1's published identity, and u1's stored contract runs it. Before, the seal was checked against the running origin (u1's), and u1 paid. Now the term carries its writer's origin (u2's), so the seal is refused (decisions 52, 53 and 63: a seal verifies against the envelope that wrote it). **Flagged for review:** this is Decision 77 read with the writer's origin, which the term now carries.
- This branch's parser pin adds `SimpleType` variants and `FixedPointPattern` from `master`. This branch has no connectives for them, so the normalizer refuses them with an error. `dev` has the connectives. The `dev` merge replaces these arms.

## 6. Known issues (Decision 88 labels)

1. **Continuations created by the normalizer's own desugaring** (`let`, `;`-sequenced receipts, synchronous send) are not sealed by the pass. The reducer's defaulting seals them at store time with the running record. Known issue: the result is the same seal, but it is not written in the term.
2. **No system process in this runtime returns a term that a caller supplied.** The check sits in the one entry for sealed terms, so a term from a system process goes through it like a received process. There is no test for that path. Known issue.
3. **The deployment-kind label is not checked against the owner.** A term of kind deployment whose owner is another signer of the same deployment passes. The kind changes nothing that the owner check does not already bound. Known issue.
4. **Lane C's `shares_membrane` is changed** (decision 9). Lane C must agree.

## Revision 2 (2026-11-06): Decisions 130 and 131, lane A1's Δ condition

### Decision 130: the running membrane

- A sealed term is "own" when its origin digest equals the running record's digest. Only an own seal gives its kind and its limit to the record that the reducer enters.
- A seal that is not own (a seal written in data and run elsewhere) is checked as before FX-21: its owner must be a signer of the running deployment or held, and it runs under the running record. Decision 12 of this log is withdrawn.
- The copy check when a receive is stored no longer refuses. The stored record takes the continuation seal's limit only when the seal is own. Otherwise the stored record keeps the running record's limit.
- Stack bodies follow the same rule. The stack-body branch runs before the seal comparison, and a non-kind signature on a stack falls through to the same owner check.
- `region_spec::data_sent_to_an_owners_contract_runs_under_the_owners_membrane_and_is_paid_there` is enabled again and passes. `seal_record_spec` is restored to its FX-19 version and passes unchanged.

### Decision 131: the smaller seal

- `CostSignature` gets `uint32 signer = 7`: an index into the origin's verified signers (0 is the deployer, then the cosigners in order). The pass writes the deployment seal as `signer 0` instead of the 65-byte deployer key.
- A signer index resolves only under its own origin. A term that names a signer index and is not own is refused (`a_signer_index_outside_its_own_origin_is_refused`). Data is not elaborated, so source cannot put an index into data.
- Every owner reference that the pass writes has an index, so no digest form was needed. Explicit seals keep the syntax that the user wrote.
- `region::resolved_owners` (FX-19's static holds) does not resolve an index. The deployment-sealed continuation's owner is the installer, which is the purse of the stored record, so the firing already holds it.

| Term | Plain | FX-21 r1 (key) | r2 (index) |
|---|---|---|---|
| `@"x"!(1)` | 15 B, 101 phlo | 137 B, 101 phlo | 65 B, 101 phlo |
| One stored continuation | 70 B, 442 phlo | 317 B, 563 phlo | 171 B, 492 phlo (+50, +11%) |
| Two stored continuations | 141 B, 899 phlo | 513 B, 1,142 phlo | 296 B, 999 phlo (+50 each) |

The rest of the increase is the elaborated seal itself (kind, the 32-byte origin digest, the limit) and the wrapper term in each continuation.

### Lane A1's condition: the default limit comes from the signed `phloLimit`

- `RuntimeOps` gets `run_limit` and `process_deploy_limited(deploy, run_limit)`. The evaluation cost is `min(run_limit, phloLimit)`. The deploy data, and so the default seal limit, keep the signed `phloLimit`.
- Test: `forms_spec::the_default_seal_limit_is_the_signed_limit_when_the_run_is_limited_below_it`. A deployment with `phloLimit` 50,000 runs with Δ = 3,000. Its cost stays at or below 3,000, and the stored seal carries 50,000.
- **For lane A2, when FX-22 merges:** FX-22's `limited()` makes a copy of the deployment with `phloLimit` = Δ, and that copy would make the default seal limit Δ. Replace `limited()` with `process_deploy_limited(envelope, committed)` in play and replay. Also record the signed envelope, not the copy, in `ProcessedDeploy`.
