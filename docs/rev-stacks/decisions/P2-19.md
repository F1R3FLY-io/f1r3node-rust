# P2-19 decisions: annotation syntax, regions and stack literals

Patch P2-19, "Annotation syntax: regions and stack literals", rev-stacks patch
plan r6.4, lane C. Branch `patch/P2-19`. All code in this patch is new. The
source branch's `authority.rs` is not ported, as the brief says.

## Base

The brief says to cut the branch from `feature/rev-stacks-ote` and to check
that P2-01, P2-15 and P2-18 are on the base. They are on three branches, not
on the phase branch. The base is the merge commit `ecb12eeaf`:
`patch/P2-15` (which carries P2-01 to P2-05 and P2-14) merged with
`patch/P2-18` (which carries P2-17 and P2-12). The merge had no conflicts.

## Decisions

| # | Decision | Alternatives | Reason | Reversible |
|---|----------|--------------|--------|------------|
| 1 | In phase 2 a signed term opens no separate charge account. Its region is the deployer's wallet, which is the wallet that P2-05 and P2-15 already charge for every COMM and every compute phlo of the envelope. | Count COMMs and compute per region in the reducer now. | Phase 2 admits only the deployer's signature (brief, design §6.3). So every region of an admitted envelope is the deployer's wallet, and the charges already land there. Per-region counts are needed only when a region can name another wallet. That is P3-02. | Yes, in P3-02 |
| 2 | The gate gets `GateInput.named` from the normalized term (Decision 30). `rev_stack::region::named_owners` walks the term and resolves each signature of a signed term and of a signed bind statically. `v6::executor::gate_inputs` compiles the deploy term with the deploy's normalizer environment and calls it. If the term does not compile, `named` is empty, and the run fails on the same parse error as before. | Parse in the gate. Resolve at run time only. | The gate must refuse before the run (Decision 30), and the gate must not depend on the normalizer (P2-04 decision 7). The executor is the caller that fills `named`. | Yes |
| 3 | The static resolution follows the reducer's binder order. A `new` binds its plain names first and its URIs after them, in `uri` order. A URI whose injection is a `GDeployerId` resolves to that key's wallet. A name bound by a plain `new`, by a receive or by a match case is unknown. A ground signature (`{% P %}[bob]`), a hash signature (`# P`) and a compound with an unknown part are unknown. | Track receive-bound names through the data. | Static analysis cannot know what a receive will bind. In phase 2, an unknown signature must be refused, so the gate must see it as foreign. | Yes |
| 4 | An unknown signature goes into `named` as `WalletOwner::Unforgeable(<prost bytes of the signature>)`. | Change the type of `GateInput.named`. | `GateInput` belongs to lane B. No real unforgeable name has this form, so the gate refuses it as `ForeignSignature`. | Yes |
| 5 | The walk includes signed terms in sent data, in quoted names and in expressions. | Only the signed terms that the deploy runs directly. | A deploy can make another process run a signed term that it sent as data. Conservative refusal is safe in phase 2. | Yes |
| 6 | The reducer checks every signed term and every signed bind when it runs. It substitutes the signature, resolves it to a wallet owner (`region::signature_owner`) and compares it with the deployer of the current run. Any other owner is a `ReduceError`. The body then runs in the same environment with the same random state. | Trust the gate. | A signed term can be stored and run later by another deployer's envelope. The run-time check refuses it there. The test `a_stored_signed_term_runs_only_for_its_signer` covers this. | Yes |
| 7 | The reducer gets the deploy data through a new field `deploy_data`, the same `Arc` that `set_deploy_data` writes. | Pass the deployer through every call. | One field. The runtime already holds this `Arc`. | Yes |
| 8 | A signed term is one more term of its `Par` in the random split, after the bundles. | — | A `Par` without signed terms keeps its split, so no existing run changes. | Yes |
| 9 | The check of a signed term charges no compute of its own. Its body is charged as usual. | Charge a fixed cost for the check. | The check is a substitution of one signature and a comparison. The design's compute table has no entry for it. | Yes |

## Stack literals: blocked

The brief makes a stack literal `s :: S` a native transfer from the writer's
wallet onto the signature channel. Open item **Q-23** ("whether contracts may
create token stacks for tokens other than REV, or every stack is REV") is
open, and it blocks P2-19 in the plan. The plan also does not say how much REV
one cell moves. The brief says to stop and ask when a decision in Open Items is
needed.

The reducer therefore still refuses a token stack, with a `ReduceError` that
names Q-23. The question went to the user on 2026-10-30 with this proposal:

- every stack is REV;
- each cell `s` moves one phlo's worth (`phloPrice` REV) from the writer's
  wallet to the wallet at `s`;
- a cell may name any signature, because a stack literal is a payment, not a
  funding region; only signed terms feed `GateInput.named`.

## Done-when

- "Charges land on the region's wallet": `v6::region_spec::
  charges_under_the_deployers_signed_term_land_on_the_deployers_wallet`. A
  signed deploy and a uniform-signed deploy are admitted, merged, settled and
  replayed. Their COMM and compute charges are debited from the deployer's
  wallet, and the COMM count equals that of the same term without the
  wrapper.
- "Other signatures refused": `v6::region_spec::
  the_gate_refuses_a_signed_term_that_names_another_signature` (gate), and
  `rholang/tests/signed_region_spec.rs` (static resolution and the run-time
  check).
- "Stack literals conserve REV": blocked on Q-23, as above.
