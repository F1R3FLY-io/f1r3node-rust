# Decisions — P1-02 (tranche 1 tests, the v6 test-network harness, docs)

Each entry gives the decision, the alternatives, the reason and whether it is reversible.

## D-P1-02-1 — Base and scope

- **Decision:** `patch/P1-02` starts at `patch/P1-13` `9c2e2afd0`, as Meredith directed on 2026-10-30. The brief (plan r7.13) asks for four things: the three-validator test, format, documentation, and coverage of the v6 helpers and the validity refusal branches. Meredith added two more: the multi-node v6 harness that the tests moved out of P1-05 to P1-12 need, and the receipt end-to-end check that P1-13 could not run.
- **Reversible:** yes.

## D-P1-02-2 — The harness goes through ShardOverrides, not task-locals

- **Decision:** `ShardOverrides` gains `v6: Option<V6TestConfig>`. The source (`5260aeda9`, and the integration branch's 0031) passed the v6 switch through `tokio::task_local!` values.
- **Alternatives:** Port the task-locals.
- **Reason:** dev's harness already threads `ShardOverrides` to `create_node`. A field there is visible in the type and needs no scope wrapper.
- **Reversible:** yes.

## D-P1-02-3 — The constructors the moved tests call

The constructors match the integration branch's names:

| Constructor | Engine started | Use |
|---|---|---|
| `create_v6_network(genesis, n)` | yes | Three-validator tests, receipts, pruning runs |
| `create_v6_network_driven(genesis, n)` | no; the test calls `tick()` | Lag tests, step-by-step checks |
| `create_v6_network_with_block_deploys(genesis, n, k)` | yes | Sets `max_user_deploys_per_block`, and with it the pool cap (P0-09) |
| `create_v6_network_with(genesis, n, V6TestConfig)` | either | Any combination |

- **Difference from the integration branch:** `create_v6_network_driven` takes no lag threshold. This base has no lag gate (P1-08 is on lane A2's branch).
- **To add the lag threshold:** when P1-14 builds on a base with P1-08:
  1. Add `lag_threshold: Option<u64>` to `V6TestConfig`.
  2. Give `create_v6_network_driven` its third argument.
  3. Pass the value in `v6_engine_for_test`.
- **Reversible:** yes.

## D-P1-02-4 — One construction point for the engine

- **Decision:** All constructors build the engine in `v6_engine_for_test` in `test_node.rs`. On this base, it calls `V6Engine::new(genesis, runtime_manager, block_store, dag_storage, deploy_storage, retained_records)` and starts the engine unless the test drives it.
- **Reason:** On `patch/P1-12`, `V6Engine::new` takes a lag threshold, a fallback distance and a policy, opens the LMDB executor state and returns a `Result`. When lane A2 merges, only this one function changes.
- **Restart tests:** they build a second engine from the node's `block_store`, `block_dag_storage`, `deploy_storage` and `runtime_manager`, which `TestNode` already exposes. The harness needs no restart helper.
- **Reversible:** yes.

## D-P1-02-5 — Shared helpers in a new harness module

- **Decision:** `casper/tests/helper/v6_network.rs` holds the steps that the integration branch repeated in each spec:
  - `engine`, `propose` (through `V6Engine::create_block`), `broadcast` and `propose_and_broadcast`
  - `wake_until`, `tick_until_idle` and `wait_for_finality`
  - `cited_records`.
- **Reason:** P1-14 ports about six multi-node specs. The specs share these steps, and the steps change together with the engine API.
- **Reversible:** yes.

## D-P1-02-6 — A driven test proposes, waits for finality, then ticks

- **Finding:** An engine orders only the blocks at or below the LFB. It fixes a block only after a later block cites its record. Blocks proposed while no engine runs carry no records, so a tick then fixes nothing.
- **Decision:** `driven_engines_advance_only_when_the_test_ticks_them` checks three things:
  - A driven engine does not run on its own.
  - A tick before any citation does work but fixes nothing.
  - Proposals and ticks in turn fix the first block on all three validators, with the same root.
- **Reversible:** yes.

## D-P1-02-7 — Plain genesis, as in tranche 1

- **Decision:** The harness uses dev's `GenesisBuilder` genesis and sets the v6 flag directly. It does not use the protocol-6 genesis of P1-03.
- **Reason:** Charging is off in phase 1, and the engine takes its limits from `ShardResourcePolicy::default()` on this base. D-P1-01h-2 (the flag set from a protocol-6 genesis) is lane A2's later step. When it lands, `v6_engine_for_test` and the genesis choice change together.
- **Reversible:** yes.

## D-P1-02-9 — The receipt end-to-end check (from P1-13)

- **Decision:** `an_executed_offer_reports_its_receipt_on_every_validator` runs on three validators.
  - One offer fires one COMM.
  - Heartbeat blocks continue until every engine retains the record of the offer's block.
  - On every validator, the receipt from `BlockAPI::offered_status` equals the record entry: outcome, COMM phlo (1), compute phlo (positive) and the number of log events.
- **Reversible:** yes.
