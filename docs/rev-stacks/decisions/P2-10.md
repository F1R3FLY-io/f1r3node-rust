# P2-10 decisions: record arithmetic and the demand cap

Patch P2-10, rev-stacks patch plan r7.2, lane B. Branch `patch/P2-10`, cut
from `patch/P2-06`. All code in this patch is new. Nothing is ported.

## Files touched

- `casper/src/rust/v6/resource_policy.rs` (genesis policy, shared with P1-03): three new fields, encoding version 2.
- `casper/src/rust/v6/block_record.rs` (lane A2's record): field 12 (the settlement) and `EnvelopeOutcome::Exhausted` (tag 3, the integration branch's tag).
- `casper/src/rust/v6/executor.rs` (shared with lane A2): the record gets the settlement, the replay compares it, an exhausted run is `Exhausted`, and replay rebuilds `is_failed` for `Exhausted` too.
- `casper/src/rust/v6/settle.rs`: the settlement wire form.
- Tests: P1-03's `v6_genesis_spec.rs` test policy lowers its `demand_cap` from 1,000,000 to 500,000 and takes the new fields from the default, because the old value breaks the new coupling.

The 0035a decision of October 28 couples the cap to the byte cap at genesis. | Yes, before any shard launches |
| 2 | The three parameters are policy fields with defaults: 1,250 millibytes of log per phlo (the 0035a measurement), 4,096 bytes per entry (r0), and 32,768 bytes per record for the close block (see memo M-7). The default demand cap is now derived: `largest_demand_cap()` = 5,846,814 phlo per block (it was 5 × 10^10). | Keep 5 × 10^10. | Caps are configuration parameters with measured defaults. 5 × 10^10 cannot meet the bound for any record byte cap. | Yes |
| 3 | Encoding version 2, 57 bytes: the four version-1 words, then the three new words. Version 1 is no longer decoded. | Decode version 1 with defaults. | No shard has launched (Decision 8). | Yes, before any shard launches |

## Memo M-7: the close block in each record

Design §6.13 counts each record as `1.25 Δ + r0` per entry, with no system
log. P1-04b decision 4 keeps dev's close-block system deploy in the record,
with its event log. On a one-validator test genesis, a record of three
envelopes is 15,794 bytes: 1,609 bytes for the entries, the gate and the
settlement, and 14,185 bytes for the close block. The close block's log
grows with the PoS work done at close, for example at epoch boundaries.

- (a) Recommended, built: a per-record allowance in the policy (`block_overhead_bytes`, default 32,768) inside the demand cap bound. This keeps P1-04b as it is. The default comes from one measurement, and it can fail at an epoch boundary.
- (b) Take the close block's log out of the record and replay it from the block instead, as the design says ("no system log"). This is lane A2's record and replay (P1-04b decision 4).
- (c) Cap the close block's log and treat a larger one as an error.

## Tests

- `v6::resource_policy`: the default policy meets the bound and equals the largest cap. One phlo more is refused. A zero rate is refused. The encoding round-trips.
- `v6::settle::proto_tests`: a settlement round-trips. A charge that is not its phlo times its price, or a credit that does not add up, is refused.
- `casper/tests/v6/gated_executor_spec.rs::a_block_record_carries_the_gate_and_replays_it`: the record carries the settlement. An exhausted envelope records `Exhausted` and is charged its whole delta. The record is within the policy bound. The record replays. A record with a forged settlement still decodes, but its replay fails.
