# Offered-funded production integration proposal

**Status:** The direct-REV path connects public ingress, proposal, publication, and independent validator replay in the current worktree. Final aggregate qualification and release approval remain pending. V2 asset conversion is tracked as pgmcp `offered-v2-third-party-conversion`. Direct-REV admission rejects V2 conversion.

**Target:** `feature/cost-accounted-rho` at base commit `e74842683`. Reuse only required cost-accounting changes from saved derivative commit `f9bd3895d`. Leave unrelated Casper consensus, finality, recovery, pruning, and general merge repairs with the Casper team.

## Selected funding rule

The saved Casper code contained a **body-only, state-bound** accounting route. The current worktree connects the **offered-funded** model to ordinary submission, proposal, block replay, and wallet and receipt settlement. Final qualification of this connection remains in progress.

The user selected a **complete selected witness** rule. The signed offer must authorize the alternatives from which a producer selects. The producer then commits one bounded, complete execution witness with its funding case. A validator must follow that witness from the authenticated root and inputs, verify every selected operation and cost, and reject an omitted operation or an incomplete cut. A producer may select only an alternative that the user authorized. The producer cannot widen source consent, price, limit, or route permissions after execution.

The [existing formal contract](signed-phlo-formal-contract.md) requires a complete family for every execution in its certified scope. Under the selected rule, that scope must be defined by the authenticated root, inputs, signed authorization, and committed complete witness. The checked family must cover the full selected case. It need not cover different authorized witnesses that were not selected. The current path connects native witness capture, validator-guided replay, and guarded publication. A completed trace without enabled-step checks and a complete-cut check does not satisfy the rule. Final qualification must confirm those checks at one candidate revision.

This milestone covers direct REV wallets, prepaid resources, and retained births. A later conversion integration will cover persistent allowances and the two V2 conversion compositions. A third party may supply a quote or perform a prior trade, but node funding still requires authenticated custody and atomic settlement of the resulting REV. Until those interfaces exist, admission accepts only V2 `NoConversion`. This milestone also supplies Embers with an atomic `SystemVault.transferBatch`, a gateway-only cross-deploy funding flow, an enforceable execution limit, and a block-bound settlement receipt.

The three-node [direct-REV integration test](../../../../casper/tests/api/offered_funded_api_test.rs) submits a signed wire envelope through the node gRPC deploy service. It verifies that changes to the signed price and limit fail at admission. After admission, the producer proposes the deploy, and independent validators replay the block. The test reads a public settlement receipt from the validator web API. It compares JavaScript Object Notation (JSON) fields for actual REV spent, phlo limit, and post-settlement purse balance with the rooted receipt. A validator also rejects an altered receipt before it publishes the block.

This test covers the combined production route. Aggregate qualification remains in progress.

## Terms and boundary

- **Offered-funded envelope:** A signed deploy that commits to offered pricing, execution limits, and funding intent. The model type is `OfferedFundedDeploy`.
- **Funding family:** Checked source capacities and all certified outcome cases. Each case carries resource obligations, eligibility, and allocation.
- **Selected witness:** A bounded commitment to the chosen native operations, their causal and match evidence, costs, failure outcome, and the complete cut for one deploy. It does not require future blocks or persistent RSpace continuations to terminate.
- **Original funding root:** The state root at which payer wallets and prepaid resources are authenticated before execution.
- **Settlement runtime root:** The root after a successful user execution, or the restored root for a classified user failure. Wallet and receipt changes apply at this root.
- **Prepaid receipt:** A rooted record for an already acquired resource. A newly born retained resource may issue a receipt after settlement, but cannot fund its own birth.
- **Host-work budget:** A separate bound on machine work and allocation. Economic phlo charges do not substitute for it.
- **Publication:** The atomic transition that makes the user result, wallet debits, receipt changes, and evidence visible to later deploys.

The intended flow is [shown here](../diagrams/offered-funded-production-flow.svg). Blue steps authenticate, amber steps prepare private evidence, green steps publish or validate, and red steps reject without leaking a partial state.

### Private purse sources in the direct-REV boundary

An unforgeable `GPrivate` name can identify a REV purse through [`vault_payer`](../../../../casper/src/rust/util/rholang/costacc/vault_payer.rs). The signed V2 `NoConversion` funding intent may name that purse as a resource source. Its signature is a `Name` authority, meaning the interpreter observed the actual unforgeable name. A `Ground` value that contains the same encoded bytes is a different authority and cannot authorize that source. The source's signed policy must contain only resource permissions for that same private authority, with exact full resource keys; it cannot pay the separate deployment fee. A signed wallet or grant source must fund the fee. This rule lets an owner fund an agent's private purse with `SystemVault.transferBatch` while retaining control of which operations may draw it.

The producer reads the purse balance at the authenticated original funding root. It derives authority from typed native execution events, matches every selected private-purse assignment to the exact signed resource key and observed `Name` event, and settles the resulting debit with the other wallets. The validator repeats that original-root read and follows the committed operation witness before it accepts the same assignment, debit, receipt, and final root. The implementation boundaries are [wallet authorization](../../../../casper/src/rust/util/rholang/costacc/direct_wallet_funding.rs), [rooted snapshots](../../../../casper/src/rust/util/rholang/costacc/direct_wallet_funding/snapshot.rs), [family selection](../../../../casper/src/rust/util/rholang/costacc/direct_wallet_funding/execution/family_selection.rs), and [independent replay](../../../../casper/src/rust/util/rholang/costacc/direct_wallet_funding/execution/replay.rs).

```text
for each selected private-purse resource assignment:
    require signed V2 source with canonical GPrivate Name custody
    require its exact full resource key in that source's signed permissions
    require an independently observed typed Name event at that key's location
    require the event's Name authority to equal the signed private authority
    require no fee allocation to the private source
    debit only its original-root authenticated REV balance
```

Prepaid credit has an additional physical-history condition. A data stack created by a legacy deploy has no prepaid receipt merely because its channel is unforgeable or its purse is funded. [Physical capture](../../../../casper/src/rust/util/rholang/costacc/prepaid_receipts/physical.rs) rejects consumption of such an unreceipted rooted stack; it cannot fabricate prior acquisition. An offered deploy may instead create a fresh datum during its own execution and pay its measured acquisition, or a prior offered deploy may issue a retained-birth receipt that a later offered deploy draws. The gateway fixture now creates its `entry` datum inside the authorized call rather than installing legacy `entry :: ()`. Focused unit tests pass for the private-source fee and permission restrictions and for rejection of a byte-identical `Ground` alias. The earlier three-node gateway test passed with body-only installer and funding deploys. The offered-only V6 variant does not pass yet. Under the protocol-6 host-work limits, replay of its `transferBatch` funding deploy exhausts the host-work budget. The replay repeatedly copies cached continuations, and profiling of that cost is pending. A trial with raised limits reached the later gateway call. That call rejects three positive resource obligations, because funding eligibility omits the installer's located purse (DR-68). The API, proposer, and independent validator receipt assertions remain unqualified for that variant.

The 64-source API test submits a signed direct-REV offer through the proposer and three nodes. It checks all 64 receipt rows against rooted balances. It also confirms that a 65-source intent fails at admission. Unused sources have distinct signed permissions, so this test isolates the configured source cap from an all-to-all funding search. A second admitted offer gives 16 payers in each resource class the same permission. Under the 128 MiB SearchStateBytes budget, its funding search exhausts the limit, and the proposer excludes it from the block. This result was checked again on 2026-10-04 with offered-only activation (DR-73) and the quarantine path (DR-72). The combined test passes with the normal 8 MiB worker stack. A trial with a 4 GiB SearchStateBytes budget admitted the dense offer after about 150 s, so that budget does not preserve this bounded rejection. This establishes bounded rejection for this dense case, not a general performance bound for every valid source arrangement.

## Funding proof: the blocking design question

The intended offer authenticates an upper execution limit, a price schedule, owner consent, source exposure, and payer identities. Actual resource obligations depend on native execution. The saved helper's type order requires a checked family before executing, but only execution supplies its measured case. Moving the existing calls around cannot resolve this cycle.

**Selected route: complete selected witness.** Authenticate a `VerifiedNativeOffer` at the original root, reserve worst-case authorized exposure and host work, and execute inside an unpublished checkpoint under the signed `phloLimit`. Capture one bounded witness that fixes the selected native operation path and complete deploy cut. Derive the exact funding case and canonical allocation from complete measurements. Verify that the user signed permission for the selected alternative and every funding source. A validator must independently execute the same signed body under witness guidance, check each operation was enabled by the rooted state and earlier witnessed effects, consume the entire journal and budget record, and compare the resulting roots, costs, failure class, and settlement. Any invalid, omitted, repeated, or extra operation rejects the candidate. A rejected candidate has no wallet charge or published effect.

The complete cut closes this deploy's selected execution. All spawned branches must finish, fail under an approved classification, or leave only persistent waiting state represented in the resulting RSpace. The cut must account for every native intent attempted before that boundary. It does not require the chain, future blocks, or persistent continuations to run to completion. Funding optimization must remain complete and canonical for the selected case; a partial search cannot silently become a valid allocation.

The [selected-witness Rocq model](../../../../formal/rocq/cost_accounted_rho/theories/SelectedNativeWitness.v) proves that an enabled, complete fixed witness has one result even when different complete witnesses have different results. It also proves that stale, unauthorized, or incomplete candidates cannot publish in its atomic model. Its `signed_authorized`, enabled-step, complete-cut, and producer/validator replay refinement inputs are explicit premises. Rust must discharge them from authenticated data and actual execution before the publication guard can open. The offer's signed price and policy commitments remain unchanged.

## Selected-witness activation gate

The earlier [state-bound exact-case proof](../../../../formal/rocq/cost_accounted_rho/theories/StateBoundCandidateFunding.v) requires one outcome for every execution in its scope. That is stronger than the selected-witness rule. The [selected-witness proof](../../../../formal/rocq/cost_accounted_rho/theories/SelectedNativeWitness.v) instead fixes one authorized witness and proves one result for that witness. Its negative examples reject an early cut and an operation after the complete cut. Neither proof establishes that the Rust reducer records every selected intent or that validators can follow the committed choice. The stale-root TLA control still shows that matching observations cannot replace a fresh-root check.

The signed body and funding intent must define the permitted-choice predicate. If their existing fields authorize every enabled execution alternative, that rule must be explicit and each selected path must still satisfy signed source and price controls. If users need to exclude some alternatives, the format needs a canonical signed selector. A producer-supplied witness cannot create consent that the signed offer did not grant.

The current private execution context accepts block data, invalid-block data, trace limits, and host-work limits from its caller. Production must authenticate the block inputs against the proposed block and derive the limits from the adopted protocol. Preflight now derives the concrete price schedule from the signed intent and binds it to adopted genesis policy. The current model does not define a separate on-chain numeric price authority.

The runtime installs live external services for validators. AI, database, and gRPC calls can return variable data or create effects outside the private checkpoint. Native-active dispatch now rejects these handlers before invocation. The focused `native_funded_runtime_rejects_external_output_before_dispatch` test passes. Replay of a captured external response alone never proves that another execution would return the same response.

`ReductionCoordinator` sorts conflicting operations by causal order. It previously ran disjoint native groups concurrently, while those groups shared one phlo reservation. A native-only global footprint key now places all native operations in one ordered group per frontier. The near-limit `native_disjoint_operations_reserve_near_limit_in_causal_order` test passes. Non-native groups remain parallel.

The operation journal checks recorded operations and independent replay. Its replay ledger rejects unused recorded slots. Native replay guides each matching operation to the committed COMM identity. It checks source and predecessor dependencies and consumes all recorded slots. The offered block path now invokes independent validator replay and compares funding, settlement, receipts, and roots. Final aggregate tests must still verify this path at one candidate revision. Native operations use causal order within each observed frontier. Every host-work failure must abort without publication.

[`SerializedNativeFrontier.v`](../../../../formal/rocq/cost_accounted_rho/theories/SerializedNativeFrontier.v) and [`NativeFrontierArrival.v`](../../../../formal/rocq/cost_accounted_rho/theories/NativeFrontierArrival.v) describe deterministic observations for a fixed frontier. The selected rule does not require all valid frontiers to be identical. It requires a canonical witness for the chosen path, an enabled-step check against authenticated state, full accounting and evidence consumption at the complete cut, and guided independent replay. The first deployable path also needs authenticated block inputs, signed authorization of the selected alternative, and verified rollback for every rejected execution.

`PreparedOfferedCandidate::authorize_publication` still fails closed for an unverified private candidate. The producer uses `authorize_publication_after_replay` after authenticated context checks, certificate validation, and independent replay. That guarded path publishes the direct-REV candidate. Since DR-102, its comparison charges the producer's acceptance budget, and the replay budget measures the certified replay alone on every role. Final qualification must verify rollback and rejection before activation.

The V2 atomic-quote model now has one explicit exact-output rule: zero output costs zero, and positive output costs an upward-rounded rational amount plus a fixed input fee. Its [Rocq proof](../../../../formal/rocq/cost_accounted_rho/theories/QuoteExactOutput.v) covers the integer arithmetic and monotonicity of that rule. The signed quote grammar also binds context, authority references, validity, custody, assets, caps, and original-input release behavior. Those syntactic and arithmetic checks do not prove that the provider owns the output, that its rooted capacity is available, or that an atomic multi-asset settlement occurred. Those runtime obligations remain part of the publication gate.

The [conversion planner](../../../../casper/src/rust/util/rholang/costacc/conversion.rs) checks quote arithmetic, shared physical holds, use limits, original-source releases, and prior-trade lineage. The metered [accepted-trade reader](../../../../casper/src/rust/util/rholang/costacc/conversion/accepted_trade.rs) reads one canonical protected receipt from authenticated history. It plans an exact old-to-new unspent-output transition and returns `IssuerUnavailable` when absent. No production native issuer writes that receipt. Receipt updates are not yet atomic with output-asset debits.

Rooted input-permission and provider-escrow records still lack production issuers. A protected-channel reader would authenticate record bytes at a root, but record presence alone cannot prove physical backing. V2 quotes name arbitrary input and output assets. `SystemVault.transferBatch` authenticates transfers of its native REV purse, while `TokenMetadata` exposes native-token metadata; neither supplies a multi-asset custody contract. Atomic quotes need an asset-custody interface that verifies input-owner and provider authority, locks both assets at the original root, issues canonical protected records bound to those locks, and atomically consumes exact old values with the asset transfers, quote-use update, funding debit, receipt replacement, and conversion fee recipient. Separate prior conversion needs an issuer that authenticates the completed prior trade and locks its unspent output before it issues the accepted-trade receipt. Validators must replay each transition independently. No such issuer or atomic publisher exists in this branch, so neither V2 conversion composition can activate.

A third party can instead complete conversion before the offered deploy and transfer settled REV into the user's purse. The resulting offer is ordinary V2 `NoConversion`: the node reads and charges that authenticated REV balance, without accepting a quote as spendable value. This route is included in the direct-REV milestone. Funding from a quote's promised output inside the same deploy requires the separate custody and settlement integration.

Live conversion requires a provider-authorized escrow record at the candidate root. That record must bind the quote, output source, available capacity, prior use, and accepted operation IDs. It also requires authenticated input permission and a receipt for any separate prior trade's unspent output. One native checkpoint must publish transfers, quote-use state, funding, releases, and receipts, with independent replay. Neither composition activates until these contracts are implemented and verified.

## Proposed end-to-end implementation

The following pseudocode summarizes the connected direct-REV path. Each stage has an owned failure boundary. The sketch does not include deferred V2 conversion.

```text
submit(envelope):
    verify canonical offered format, signatures, owner consent, and genesis policy
    authenticate wallets and prepaid inventory at original_root
    freeze signed controls, price, exposure, and execution context
    prepare a bounded private candidate at original_root

prepare(candidate):
    run native user execution under phloLimit and host-work limits
    capture complete operation journal, budget record, events, and byte observations
    derive prepaid draws from original-root receipts and measured demand
    derive retained births from actual authority and physical stacks
    prove the chosen funding-family contract and calculate exact settlement
    reject if any recording, match, backing, price, or bound is incomplete

publish(candidate):
    recheck original-root funding inputs and current settlement root
    under one owned checkpoint, apply user result, wallet debits, and receipt changes
    commit canonical evidence and the adjacent pre-state and post-state roots
    on any failure, restore the checkpoint and release private resources

validate(processed):
    load the historical rule selected by the authenticated envelope format
    independently replay from the submitted pre-state root and original funding root
    regenerate demand, prepaid selection, births, family, and settlement
    compare complete journal, costs, failures, receipts, and both resulting roots
    accept only after full evidence consumption and exact equality
```

The original funding root and settlement runtime root must remain distinct. This matters when successful user execution changes RSpace before wallet settlement. It also matters when a classified user failure restores the user checkpoint but retains only authorized billable work. Platform, certificate, and unclassified failures must not publish candidate charges, as required by [economic policy](economic-activation-policy-ratification.md).

The evidence field uses `ProcessedDeployProto.nativeCostEvidence` at field 14. The field is absent in historical records. The historical decoder rejects a present field unless the funded decoder verifies it. `NativeCostEvidenceV1` has a domain and fixed field order. It carries the envelope, genesis policy, schedule commitments, and three state roots. It records execution phlo, fresh and retained phlo, limit, price, fee, and failure class. Bounded sections contain budget recording, operation journal, funding case, prepaid delta, and wallet settlement. Every field uses an eight-byte length prefix. Fixed-width fields reject other widths, and the decoder rejects trailing bytes and over-limit input. The bounded nested codecs are connected to producer and independent replay. Final aggregate qualification remains pending. A digest alone is insufficient because replay must reconstruct operation directives.

The funding-case section now has a bounded canonical codec for source capacity, exposure, hold, debit, fee and refund; encoded obligation keys, quantities and amounts; eligibility and assignment cells; and resource/fee cursor witnesses. Its decoder checks strict source/key order, matrix dimensions, and conservation. The prepaid section records ordered physical stack draws and exact demand positions, retained stack birth digests, and separate receipt old-value/replacement digests. Separating births from receipt transitions matters because several born stacks can update one receipt bucket. The accepted block decoder requires both sections to parse. Publication still requires independent regeneration of every section from the authenticated original root and replayed execution; a syntactically valid section alone is not certification.

The version-6 syntax bounds are fixed by `offered_funded_v6_limits()`: 1 MiB for an envelope, 256 KiB for funding intent, 64 signers and direct sources, 1,024 resource permissions, 4,096 authority nodes, and 4 MiB for native evidence with a 1 MiB maximum field. These bounds apply identically at ingress, pending storage, block decode, and replay. They bound parsing independently of operator transport settings. Format activation and economic schedule selection still come from the adopted approved-genesis policy; parsing an offered record does not activate it.

The authenticated schedule fixes the separate deployment fee at one atomic REV. Execution phlo includes work that an existing prepaid receipt may cover. Newly retained resources are a separate acquisition. The offered evidence therefore records execution `phloUsed`, `freshPhlo`, and `retainedPhlo` separately. It must satisfy `freshPhlo ≤ phloUsed` and `phloUsed + retainedPhlo ≤ phloLimit`. The wallet pays `(freshPhlo + retainedPhlo) × phloPrice + 1` atomic REV, while `phloLimit × phloPrice + 1` remains the signed maximum REV debit. A new retained birth must match exactly one complete resource identity in the signed source permissions, including its physical channel, cell authority, selected schedule terms, and resource class. Ambiguous class permissions reject the candidate. The price field in the genesis policy is neutral; execution must bind a concrete selected schedule with the signed offered price before it computes either amount.

Independent validation must never accept a helper's precomputed allocation or receipt list on trust. It must regenerate them from authenticated state and replayed demand. Each accepted deploy advances the block's root before the next deploy. Private evaluations may run independently, but shared-wallet or shared-receipt candidates need a root and old-value check at publication. A stale candidate retries without duplicate charges.

## Connected implementation batches and exit evidence

1. **Contract decision and authenticated ingress.** Prove or reject the state-bound exact-case refinement. Define the envelope activation rule and canonical evidence schema. Connect public submission through pending storage and proposal without body-only conversion. Evidence: wrong format, price, consent, root, and schedule reject before publication.
2. **Candidate producer and prepaid backing.** Implement the approved family producer, measured demand projection, deterministic prepaid selection, retained-birth capture, and host reservations. Evidence: fresh, prepaid, mixed, retained, malformed, and exhausted cases; payer counts through the configured cap; conservation and no same-attempt prepaid birth.
3. **One transaction and replay.** Connect ordinary execution to a single outer checkpoint and publish complete evidence. Connect independent validator replay and exact root comparison. Evidence: cold/warm parity, user failure, platform failure, duplicate settlement, foreign root, retry, cancellation, and concurrent independent sessions.
4. **Protocol qualification.** Test every accepted historical format under its historical rules and the new format under fresh-genesis policy. Run model/property, Rocq, TLA+/Apalache, Loom, integration, formatting, Clippy, documentation, and security gates on one pinned candidate. Multi-node results must show matching state, funding, and receipt roots.

The direct-REV implementation batches are connected in the current worktree. The fourth batch remains a release gate. A failed proof or an unbounded complete-family producer blocks activation. The pending aggregate tests are acceptance criteria, not claims of completed verification.

## Post-mortem: why the gap was missed

**Observed facts.** The [implementation guide](README.md) already separated the current non-Casper milestone from later Casper production bindings. The [verification catalog](../cost-accounted-rho-verification.md) states that native COMM fixtures supply an explicit funding case and prepared prepaid state. They do not prove complete family generation or production receipt issuance. [Observed funding outcome](observed-funding-outcome.md) states that ordinary funded directives and ingress remain disabled. The saved derivative branch has native helper APIs, while its ordinary proposer and replay path still convert to body-only envelopes. Rocq's [`state_bound_certificate_funds_committed_cost`](../../../../formal/rocq/cost_accounted_rho/theories/EndToEndAuthority.v) assumes a valid certificate and equal committed/replayed cost; it does not construct the certificate from a public deploy.

**Assessment failure.** My earlier completion claims treated a real body-only accounting path as evidence that the newer offered-funded path was production-connected. I also treated direct helper tests and conditional formal theorems as proof of ordinary ingress-to-replay reachability. That was wrong. I further described this gap as blocking the current narrowed milestone, despite the explicit branch split in the guide. The present review corrects both errors.

**Likely contributing factors, not independently established historical causes.** The large saved Casper diff mixed cost-accounting support with unrelated Casper work, which made route ownership harder to see. Several conformance statements describe a completed older state-bound route beside caveats for offered funding. Reviews focused on local invariants, fixtures, and proof premises rather than tracing a user submission through every production call site. These factors explain how a green local test or proof result could be overread, but they do not excuse the mistaken scope and completion statements.

**Prevention.** Future completion reviews must map each advertised format from public ingress to proposer, stored block, independent replay, settlement, and state publication. Each link needs a non-test production caller and a failure test. Verification reports must state theorem premises and supplied fixture data beside the claimed result. Release status must distinguish body-only state-bound accounting, lower-layer offered funding support, and actual offered-funded activation. A full public-submission-to-peer-replay test must be a gate before claiming the latter complete.
