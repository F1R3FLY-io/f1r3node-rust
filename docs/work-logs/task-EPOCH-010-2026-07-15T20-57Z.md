# EPOCH-010: Soak Benchmark Metrics & Reporting — design handoff

## What this is

US-004 (docs/UserStories.md) captures the story: make the 72-hour merge-recovery
soak produce comparable benchmark metrics instead of pass/fail only. This log
records the delivery design agreed with the maintainer (human-jeff) on
2026-07-15, so the implementing agent does not re-litigate settled decisions.

## Settled decisions (maintainer-confirmed)

1. **Cadence**: the 72h soak concludes **Mondays** (starts Fridays). One report
   cycle per week, produced at soak conclusion. Do not add extra scheduled runs.
2. **Metrics** (all four, week-over-week): failure rate, iteration throughput,
   peak node RSS, deploy-to-finalization latency.
3. **Delivery is a hybrid**:
   - **GitHub Pages trend dashboard** (pull): repo is public so Pages is free;
     site will be at `https://f1r3fly-io.github.io/f1r3node-rust/`. Full detail
     and cross-week charts live here.
   - **OCI Notifications Service email** (push): plain-text Monday summary
     (four metrics + deltas + verdict + dashboard link). Chosen over raw
     SMTP because the soak already runs on self-hosted OCI runners —
     instance-principal auth means **no new GitHub secrets** — and ONS handles
     confirmation/unsubscribe links so no recipient list is maintained in-repo.
4. **Regressions gate releases** (maintainer's explicit choice over
   alert-only): a threshold breach marks the soak run failed and the release
   workflow must not promote until a soak passes or a maintainer overrides.

## Alternatives considered and rejected (with reasons)

- **Email-only (SMTP/SES)**: needs mail credentials in GitHub, a manually
  maintained recipient list (PII, churn), HTML rendering pain. Rejected in
  favor of ONS which the org already operates (budget alerts use it).
- **Auto-posted GitHub Discussions**: viable push channel with self-service
  subscriptions (repo has Discussions enabled), but maintainer directed
  evaluation of the OCI email service instead; keep Discussions in mind as a
  cheap later addition — the weekly summary markdown could be dual-posted.
- **Bot-committed markdown reports in-repo**: pollutes history; this repo's
  per-commit consent culture makes an auto-committer a poor fit.
- **Job summary/artifacts only**: buried in Actions; fails the goal.

## Implementation pointers

- Soak entry point: `scripts/run-merge-recovery-soak.sh` — already writes
  per-iteration dirs (`iteration-NNNNN-<provider>/`) with `pytest.log` and
  `exit-code.txt`, and an `iterations=` summary block at the end. TASK-010-1
  extends this, it does not replace it.
- Workflow: `.github/workflows/merge-recovery-soak.yml` — duration resolution
  already maps to 86400/259200s; artifact upload step exists for logs.
- Load test being looped: `integration-tests/test/tests/custom/test_load.py`
  in the system-integration repo (`SYSTEM_INTEGRATION_DIR`).
- RSS sampling precedent: the harness `test/infra/resource_monitor.py`
  (system-integration) already samples total node RSS — reuse its output for
  the subprocess provider rather than re-instrumenting.
- Finalization latency precedent: `scripts/bench/profile-casper-latency.sh`
  (EPOCH-009 / TASK-009-5) parses Rust JSON logs (`f1r3fly.propose.timing`,
  `f1r3fly.casper`) for p50/p95 — same parse targets apply here.
- Pages deploy: use the official `actions/deploy-pages` route (Settings →
  Pages → source "GitHub Actions"); keep the metrics history as JSON files in
  the site payload so TASK-010-3 can fetch last week's summary from it.

## Related context (why this exists now)

The 2026-07-15 merge train (PRs #122, #123) landed the merge-recovery port on
dev, and the fairness-gate incident (see PR #122 discussion; revert commit
bb3ad9b4) demonstrated exactly the failure mode this epoch guards against: a
consensus change that passed unit tests but blew node RSS to 7GB and stalled
finalization under sustained load. Peak-RSS and finalization-latency trends
from a weekly soak would have caught it before merge.
